# 공개 공고 검색 DB 연결

담당: 민규. 신규 SQL 구현과 롤백형 SQL 테스트를 제공한다. 실제 DB 실행 결과는 [민규 현황](../../docs/collaboration/minkyu.md)을 확인한다. 종현의 제품 검색 계약·서비스·저장소 코드를 대신하지 않는다.

## 호출 경계

`public.search_public_posts`는 `anon`, `authenticated`, `service_role`에서 실행 가능하다. 로그인 여부·마스킹은 검증된 DB 세션의 `auth.role()`·`auth.uid()`로 판단한다. 클라이언트에서 사용자 ID나 표시 권한을 인자로 받지 않는다. 회원 검색은 사용자 JWT를 전달해야 하며 서비스 키로 대신 검색하면 비로그인 별칭을 받는다.

| SQL 인자 | 기본값·조건 |
|---|---|
| `p_query text` | null 또는 공백은 전체 목록. 최대 300자. 대소문자 무시 문자 그대로 부분 일치; `%`, `_`는 와일드카드가 아니다 |
| `p_date date` | null 또는 유한한 날짜. 공고 시작의 `Asia/Seoul` 달력 날짜 일치 |
| `p_category text` | null 또는 기존 posts 카테고리: 지금·전시·축제·식사·운동·여행·클래스·산책·스터디·공연·쇼핑·기타 |
| `p_area text` | null/공백 또는 최대 60자 공개 지역 접두어. 좌표·반경·거리 기능 없음 |
| `p_after_starts_at timestamptz`, `p_after_id uuid` | 둘 다 null인 첫 페이지 또는 이전 결과의 커서 두 값을 함께 전달. timestamp는 유한값 |
| `p_limit integer` | 기본 20, 1~50. 명시적 null·범위 밖 값은 거절 |

DB JSON 예시는 다음과 같다. HTTP 계층은 이 객체를 공통 `{data, requestId}`의 `data`로 감싼다.

```json
{
  "items": [{
    "postId": "92000000-0000-4000-8000-000000000001",
    "title": "전시 동행",
    "publicArea": "서울특별시 성동구 성수동",
    "authorDisplayName": "동행-92000000000040008000000000000001"
  }],
  "nextCursor": {"startsAt": "2026-10-01T03:00:00+00:00", "postId": "92000000-0000-4000-8000-000000000001"}
}
```

마지막 페이지는 `nextCursor:null`, 0건은 `items:[]`다. 시작 시각·ID 오름차순의 keyset 페이지이며 같은 시작 시각도 ID로 정렬한다. 커서는 공개 일정 기반의 페이지 메타데이터이며 권한 토큰이 아니다. 목록 요청 사이 데이터 변경까지 고정하는 snapshot은 아니다. 별칭은 공고 ID 기반이므로 같은 공고에서 안정적이고 여러 공고의 작성자를 별칭으로 연결하지 않는다. 로그인은 기존 `mask_real_name` 규칙을 적용하며 본인·확정 당사자도 이 경로에서 전체 실명을 받지 않는다.

## 검색과 저장의 분리

- `recruiting`, 모집 마감 전, 시작 전 공고만 반환한다. 삭제·마감·모집 시간 만료는 제외한다.
- 일치 대상은 제목, 분리 저장한 등록 장소명·등록 주소다. 소개·공개 지역·후기·상세 만남 지점은 키워드 일치에 쓰지 않는다. 공개 지역은 별도 `p_area` 필터다.
- 등록 위치는 `private.post_search_locations`에만 저장하며 RLS를 켜고 일반·서비스 역할의 직접 테이블 접근을 모두 회수했다. 보안 정의자 RPC 안에서만 비교한다. 최소 카드에 등록 주소·장소명·일치 조각·원본 실명·작성자 ID를 추가하지 않는다. 기존 `public.posts`와 `list_posts`에 위치 컬럼을 추가하지 않았다.
- 기존 `exact_location`은 자동 파싱·이행·검색하지 않는다. 별도 입력이 없는 기존 공고는 제목으로만 키워드 검색된다. 주소 검색 결과의 존재에서 장소를 추정할 가능성 자체는 제거하지 못한다.
- `public.set_post_search_location(p_post_id uuid, p_registered_place_name text, p_registered_address text)`는 **service_role만** 호출한다. 주소 trim 후 1~300자, 장소명은 null/공백이면 없음 또는 1~200자다. 행 잠금 후 살아 있는 공고에 upsert하며 반환은 void다.
- 이 쓰기 RPC는 미래 공고 서비스의 내부 연결점이다. 브라우저에 서비스 키를 노출하지 않으며 서비스에서 작성자·입력 출처·등록 주소와 상세 안내 구분을 검사해야 한다. 현재 공고 생성 RPC는 아직 이 연결점을 호출하지 않는다. 위치 재입력은 기존 검색 값을 대체하며 과거 혼합 상세값은 그대로 보존한다.

## 오류·이전 경로·남은 연결

잘못된 검색 인자는 SQLSTATE `22023`/`invalid_input`, 없는/삭제 공고 위치 쓰기는 `P0002`/`post_unavailable`, 위치 테이블·쓰기 RPC의 일반 호출은 `42501` 권한 거절이다. DB 오류 원문을 HTTP로 보내지 말고 공통 공개 오류로 변환한다.

이번 구현은 신규 RPC에 대한 검색 정책이다. **기존 `list_posts`와 공개 posts 직접 조회는 유지돼 소개·공개 지역 검색이 여전히 가능하다.** 기존 경로에는 새 private 위치 데이터가 노출되지 않지만 최신 검색 범위의 전체 서비스 적용은 종현 검색 어댑터 전환과 민규의 이전 API 전환 작업 이후다. 기존 반환 계약을 조용히 변경하거나 기존 클라이언트를 파손시키지 않았다.

현재 posts에는 비용 컬럼이 없어 비용 필터를 지원하거나 기존 공고를 무료로 추정하지 않는다. 작성자 나이 범위·날짜 구간 필터 및 확장 카드도 아직 이 최소 DB 경로의 범위 밖이다. 제품 계약에 맞춰 후속 추가하며, 어댑터는 미지원 조건을 조용히 무시해 검색하지 않는다. 금액/계좌·PASS·제공사·미정 운영 정책을 이 migration에서 결정하지 않는다.

## 검증

`tests/database/minkyu/public_post_search.sql`을 정식 이력과 신규 migration을 적용한 **격리 로컬 DB**에서 owner로 실행한다. 전체 테스트는 transaction 마지막에 rollback한다. 제목·장소명·주소, 소개·상세 제외, 문자 리터럴, 날짜·분류·지역, 동시각 페이지, 빈 결과, 범위 오류, 비로그인 별칭·회원 마스킹, 일반 역할 쓰기/원문 거절, 서비스 upsert, 이전 자료 보존을 검사한다. 실제 다중 세션 경쟁·부하·HTTP 연결 검사는 이 파일의 검증 범위가 아니다.
