분석일: 2026-09-14 · 코드 기준: `56475ab15868d6c036c0e66199054360bc92ef24` · 화면 확인: https://yumidang.vercel.app

현재의 핵심 문제는 **상대 확인 → 확정 전 대화 → 동행 결정 → 완료 → 평가**가 하나의 관계와 상태로 연결되지 않는다는 점이다. 화면은 여럿 있지만, 오늘 MVP가 검증하려는 판단 과정을 충분히 경험할 수 없다. 또한 문서 자체에도 서로 다른 확정 규칙과 미결정 항목이 있다. 구현자의 문서 열람 여부나 의도는 이 분석으로 판단하지 않는다.

이번 작업은 문서 대조와 현행 화면 재현이다. 앱 코드·노션 원문·배포는 변경하지 않았다. 실제 SMS·결제·통화·DB 운영 기능의 부재를 프론트 프로토타입의 결함으로 일괄 판단하지 않았다. 가상 데이터라도 사용자 역할, 표시 정보, 버튼과 상태의 연결은 맞아야 한다.

오늘 문서는 최종 매칭에서 끝내지 않고 **실제 동행 완료와 평가까지 한 사이클**을 요구한다. 완료·평가를 임의로 범위 밖으로 돌리면 안 된다. 다만 ‘3분 안에’와 실제 만남·7일 평가기간은 실제 시간으로 함께 수행할 수 없으므로, 발표·테스트에서는 시작 전/동행 후 상태를 명시적으로 전환하는 시연 장치가 필요하다. 시간이 오지 않았는데 일반 사용자의 완료 버튼이 항상 작동하는 방식은 잘못된 정책을 보여준다.

## 3. 우선 바로잡을 연결

### F01. 신청과 확정 전 채팅이 연결되지 않음 — 핵심 검증 차단

- **문서:** MVP `REQUESTED → MATCHING → CONFIRMED`, MATCH-02, CHAT-01~04. 신청 후 상대를 더 알아보고 최종 판단한다.
- **현재:** 신청 상태는 `pending / accepted / rejected` 세 가지다. 받은 신청에는 프로필·대화 진입 없이 수락/거절만 있다. 수락하면 약속을 생성하고 채팅 탭을 연다. 채팅에는 요청 ID·방 ID·대화 목록이 없고 선택된 확정 약속 한 건만 전달된다.
- **영향:** 전시 공고에 신청해도 그 사람과 확정 전에 대화할 수 없다. 기본 채팅에서는 식사 약속용 문구가 나온다. Q3를 검증하기 어렵다.
- **보완 방향:** 참여 요청과 채팅방을 연결하고, 대화방 상단에 연결 공고·현재 상태·최종 결정 동작을 둔다. 확정 후에도 같은 대화방을 유지한다.
- **주의:** MATCH-03은 ‘채팅 없이 즉시 수락도 가능’이라고 명시한다. 따라서 즉시 수락 자체를 무조건 오류라고 단정하지 않는다. 확정 전 대화 경로가 없는 것은 명백한 누락이며, 대화를 필수로 할지는 6절의 결정 대상이다.
- **코드:** [JoinRequest 상태](../../../src/types.ts), [Me 신청 카드](../../../src/components/CompanionRequests.tsx), [App 수락 처리](../../../src/App.tsx) 524~579행, [채팅 초기 상태](../../../src/components/ChatView.tsx) 15~56행, [신청 안내문](../../../src/components/JoinRequestModal.tsx) 146행.

### F02. 상대를 판단할 프로필 경로와 근거가 부족함 — 핵심 검증 차단

- **문서:** MVP 프로필 P0, PROFILE-01~05, TRUST-02. 사진·마스킹 이름·나이 공개 정보·성별·성향·취미·소개·완료 동행·후기·KYC를 보고 판단한다.
- **현재:** 공고 상세 작성자 사진/이름은 대화형 요소가 아니다. 상대 공개 프로필 화면과 취미·성향 데이터가 없다. 상세·신청·채팅·대시보드에는 ‘당도 99’가 고정되어 있고, 상세에는 인증회원도 조건 없이 표시된다. Me의 참여 14회·평점 5.0도 고정값이다.
- **영향:** 사진과 점수만 보고 신청하게 되며, 어떤 신뢰 근거가 결정에 영향을 주었는지 관찰하기 어렵다. 새 계정과 경험 많은 예시 계정의 차이도 드러나지 않는다.
- **보완 방향:** 공고와 요청자 카드 양쪽에서 같은 공개 프로필로 이동. 한 사용자의 정보·당도·평가 근거는 공통 데이터에서 가져온다. 신규 계정과 체험용 기존 계정을 구분한다.
- **코드:** [PostDetailModal](../../../src/components/PostDetailModal.tsx) 98~121행, [MyPageView](../../../src/components/MyPageView.tsx) 143~193행, [CurrentUser](../../../src/types.ts) 119~139행.

### F03. 대화가 탭 이동으로 사라짐 — 실행 재현

- **문서:** AUTH-05의 상태 복원, CHAT-02/04의 공고·요청별 대화 보존.
- **재현:** 채팅에서 메시지 전송 → 홈 이동 → 채팅 복귀. 방금 보낸 메시지의 화면 내 개수가 **1 → 0**이 된다. 새로고침 없이 발생했다.
- **원인:** 메시지를 ChatView 내부 useState에 저장하며 탭 이동 때 컴포넌트가 제거된다. 복수 약속을 추가해도 채팅은 약속별 방 목록이 아니다.
- **보완 방향:** 대화를 방 ID별 공통 상태로 관리. 프로토타입에서도 탭 이동은 보존해야 한다. 새로고침 보존은 테스트 방식에 따라 로컬 저장 또는 명시적 초기화로 설계할 수 있다.
- **코드:** [ChatView](../../../src/components/ChatView.tsx) 32~51, 69~93행, [App 채팅 탭](../../../src/App.tsx) 849~863행.

### F04. 시작 전 완료·평가가 가능하고 중복 정산됨 — 실행 재현

- **문서:** COMPLETE-01/02, REVIEW-01/02. 약속 시작 전 완료 금지, 완료 후 당사자별 1회 평가, 양측 제출 또는 7일 경과 후 공개.
- **재현:** 홈 **D-2** 약속 → ‘동행이 잘 끝났어요’ → 평가 제출이 가능하다. 이어 ‘상대방 제출 즉시 시뮬레이션’을 누르고 자동 타이머를 기다리면 내 당도가 **50 → 54**, 받은 후기가 **2 → 4**가 된다.
- **원인:** 완료 동작은 평가창을 여는 것뿐이다. 완료 여부는 상대 평가 시뮬레이션 뒤에 바뀐다. 수동 시뮬레이션과 2.2초 타이머가 각각 정산을 호출하며 중복 방지 조건이 없다. 내가 제출한 평가 payload는 App에서 저장되지 않고 알림만 만든다.
- **보완 방향:** 동행 완료와 평가 제출을 서로 다른 상태 전환으로 분리. 평가·공개·당도 반영을 약속/평가자 기준 한 번만 처리. 시연 시간 전환은 명시적으로 제공.
- **코드:** [App](../../../src/App.tsx) 651~697행, [ReviewModal](../../../src/components/ReviewModal.tsx) 49~82, 278~285행.

### F05. 당도 정책이 명세와 다름

- **문서:** MVP 기본 당도 15, TRUST-01 초기 15·최대 100·정수. 완료 횟수 자체는 가산하지 않음. 긍정/부정 후기 버튼과 별점 기준으로 가감. TRUST-03 갱신 주기 7~10일.
- **현재:** 로그인·가입 모두 50으로 시작한다. 상대의 별점 5와 긍정 문구를 만들어 언제나 +2 정산한다. 긍정/부정 후기 선택 UI, 7일 공개기한, 분쟁 보류, 유효 평가 재계산은 없다. ‘만남 완료 보상’이라는 표현도 있다.
- **보완 방향:** 표시값만 15로 바꾸는 것으로 끝내지 않고, 평가 입력 → 공개 가능 여부 → 유효성 → 계산 → 같은 프로필에 반영하는 연결을 맞춰야 한다. 갱신 주기는 별도 결정 대상이다.
- **코드:** [AuthModal](../../../src/components/AuthModal.tsx) 164~179, 226~243행, [ReviewModal](../../../src/components/ReviewModal.tsx) 66~82, 317~318행, [MyPageView](../../../src/components/MyPageView.tsx) 135~154행.

### F06. 개인 정보와 장소 공개가 관계·권한에 연결되지 않음 — 실행 재현

- **문서:** AUTH-05는 개인 채팅·매칭 접근을 로그인 사용자로 제한한다. DISC-03/MATCH-06은 매칭 전 상세 장소 제한 및 확정 당사자 이용을 요구한다.
- **재현:** 비회원이 채팅 탭에서 메시지를 작성할 수 있다. 비회원이 마감된 브런치 공고를 열면 ‘매칭 확정자 전용 상세 장소’와 ‘2층 카운터 앞 창가 예약석’이 보인다.
- **원인:** 상세 장소 조건이 `isHost || isClosed`다. 공고 마감 여부와 내가 해당 매칭의 당사자인지는 다른 조건인데 함께 취급한다. Appointment에도 참여자 ID가 없다.
- **보완 방향:** 공개 공고 보기와 개인 대화/약속 보기를 분리하고, 해당 관계의 당사자인지 판단한다. 샘플 화면에서도 같은 규칙으로 표시해야 한다.
- **제한:** 실제 개인정보 유출을 발견했다는 뜻은 아니다. 예시 데이터의 노출 규칙 오류를 재현했다. AUTH-07에는 로그아웃 후 개인 정보 접근 가능이라는 반대 문구가 있어 문서 정정도 필요하다.
- **코드:** [PostDetailModal](../../../src/components/PostDetailModal.tsx) 195~202행, [App](../../../src/App.tsx) 849~863행, [Appointment](../../../src/types.ts) 43~64행.

## 5. 자연스럽지 않은 이유를 상태로 보면

현재 객체는 공고와 요청 중심으로 시작하지만, 채팅·약속·후기가 동일한 관계를 계속 참조하지 않는다.

| 연결 | 현재 단절 | 필요한 기준 |
| --- | --- | --- |
| 사용자 → 공개 프로필 | 이름·사진·점수 복사, 후기 등 고정값 | user_id로 기본 정보와 신뢰 근거를 일치시킴 |
| 공고 → 참여 요청 | 변경·마감·삭제의 결과가 요청에 전달되지 않음 | 공고 상태/조건 버전과 요청의 유효성 연결 |
| 요청 → 채팅 | request_id에 연결된 채팅방 없음 | 요청별 방과 확정 전 상태 |
| 채팅 → 확정 동행 | 선택 약속만 전달, 대화가 독립 상태 | 같은 방을 유지하며 match_id·확정 조건 연결 |
| 확정 → 완료 | 평가를 완료 처리 대신 사용 | completed_at과 완료 가능 조건 분리 |
| 완료 → 평가 → 당도 | 내 제출값 미저장, 고정 상대 평가, 중복 가산 | 당사자별 평가와 공개/유효성/반영 이력 연결 |
| 알림 → 원래 대상 | 일반 알림에 대상 ID와 이동 없음 | 대상 유형·ID·변경 사유·현재 접근 상태 |

**추천 체험 흐름:** 공고 선택 → 상대 공개 프로필 → 신청 → 해당 상대와 매칭 중 대화 → 최종 확정 또는 종료 → 확정 상세/Me/홈 리마인드 동기화 → 동행 후 상태 전환 → 완료 → 평가 → 공개 프로필 신뢰정보 갱신.

이는 다음 구현의 기준안이지 이번에 구현한 동작이 아니다. 아직 핵심 정책 결정을 대신 확정하지 않았다.

## 6. 문서에서 먼저 맞춰야 할 세 가지 판단

### 1) MATCHING에 언제 들어가며, 누가 최종 확정하는가?

- 오늘 MVP: `REQUESTED → MATCHING → CONFIRMED`, 확정 전 대화가 Q3의 핵심.
- 기능명세 CHAT-01: 요청 후 채팅 활성화. MATCH-03: 작성자 수락 시 즉시 확정, 채팅 생략 가능.
- **추천 기준안:** 요청 후 연결 채팅을 제공하고 ‘매칭 중’으로 표시한다. 대화 후 작성자의 최종 수락을 기존 명세의 확정 동작으로 유지한다. 오늘 회의가 ‘양측이 각각 최종 동의’까지 뜻했는지는 확인 필요하다.
- 별도 근거 없이 ‘첫 수락=대화 승인, 두 번째 수락=최종 확정’ 같은 단계를 새로 만들지 않는다. 테스트에서 대화 경험을 관찰하는 것과 제품에서 대화를 강제하는 것도 구분한다.

### 2) 가입·프로필·완료·평가 중 어디까지 3분 체험에 넣을 것인가?

- 문서는 최초 프로필 등록과 완료·평가까지 포함하지만, 3분 목표도 함께 제시한다.
- **추천 기준안:** 앱에는 전체 흐름을 유지하고, 주 테스트에서는 미리 준비한 체험 계정으로 공고·프로필·대화·결정에 집중한다. 가입과 동행 후 평가를 확인할 때는 별도 시작 상태로 전환한다. 가입·평가를 삭제하자는 제안이 아니다.
- 모든 단계를 3분에 꼭 넣어야 한다면 입력량·예시값·시간 전환을 명시적으로 설계해야 하며, 빠르게 눌렀다는 것을 실제 가입 의향·동행 성사로 해석하지 않는다.

### 3) 완료 권한·당도 공개/갱신은 어떤 기준으로 시연할 것인가?

- COMPLETE-01의 ‘동행 요청자’가 공고 작성자인지 참여 신청자인지 불명확하다. `약점 논의MD`도 이 점을 미결정으로 표시한다.
- 별점/후기 가감 기준과 초기 당도 15는 명확하지만, 하한·합산 방식·7~10일 중 실제 갱신 시점 등에는 결정 여지가 있다. 블라인드 7일 공개와 당도 갱신도 연동해야 한다.
- **추천 기준안:** 역할명을 공고 작성자/참여 요청자로 통일하고 완료 권한을 정한다. 시연에서는 평가 대기·공개·반영 단계를 명시하며, 같은 평가를 한 번만 반영한다. 실시간 증가를 정식 정책으로 먼저 굳히지 않는다.

## 7. 추천 수정 순서

1. **한 관계의 기준부터 정리:** 사용자·프로필·공고·요청·대화방·확정 동행·평가 ID와 상태를 연결하고, 6절의 확정 방식과 역할을 정한다.
2. **Q2/Q3 체험을 먼저 완성:** 공고 → 상대 프로필 → 참여 요청 → 매칭 중 대화 → 최종 결정. 보낸/받은 신청, 채팅 목록, 알림이 같은 상태를 가리키게 한다.
3. **되돌림·예외를 연결:** 요청 취소, 거절 사유, 다른 후보 확정, 공고 마감/변경/만료, 일정 변경, 확정 취소·차단, 비회원 접근과 장소 공개.
4. **동행 후 신뢰 순환:** 완료와 평가 분리, 공개 대기, 중복 방지, 기본 당도 15 및 평가 근거의 프로필 반영.
5. **화면 세부와 시연 준비:** 생년월일·남성 인증 선택지·취미/성향·소개·사진 저장, 일정 필터, 예시/후속 기능 표시. 실제 사용자 테스트가 가입을 포함하면 가입 보완을 2번보다 먼저 수행한다.
6. **합의한 프론트 흐름을 바탕으로 DB·외부 연동:** 오늘 회의의 프론트→DB→테스트 방향을 유지. 행사 수집과 자연어 탐색은 각각 별도 데이터 연결 작업으로 계획한다.

새 화면을 더 붙이기 전에 2번 흐름이 현재 문서의 Q2/Q3를 관찰할 수 있는지 확인하는 것이 가장 직접적인 개선이다. 완성된 프로토타입은 버튼이 눌리는 것뿐 아니라, ‘이 사람을 왜 선택했고 대화 후 생각이 어떻게 바뀌었는가’를 사용자가 설명할 수 있어야 한다.
