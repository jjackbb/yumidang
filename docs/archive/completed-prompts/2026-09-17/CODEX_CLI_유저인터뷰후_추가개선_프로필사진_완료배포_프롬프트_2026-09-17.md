## 3. 작업 트리 보호와 변경사항 통합

현재 작업 트리에는 프로필 사진 기능의 커밋되지 않은 변경이 있습니다.

- 기존 변경을 버리거나 `reset`, `checkout`, `restore`, stash로 숨기지 마세요.
- 어떤 변경이 사진 기능, 인터뷰 개선, 이전 사용자 작업에 속하는지 먼저 분류하세요.
- 같은 파일을 수정하는 개선사항은 기존 사진·성별 분기 구현을 보존하며 통합하세요.
- 기존에 사용자가 만든 변경을 덮어쓰지 마세요.
- 새로운 핵심 정책을 임의로 추가하지 마세요.

현재 로컬 사진 구현에서 반드시 유지할 계약:

- 신규 가입 기본 프로필에서 사진 필수
- JPG/JPEG/PNG 원본 10MB 이하
- 긴 변 최대 480px, JPEG 품질 0.82 변환
- private `profile-images` bucket
- DB에는 signed URL이 아닌 `<auth.uid()>/<uuid>.jpg` 경로 저장
- 서버가 객체 존재, MIME, 크기, 경로와 소유권 검증
- 업로드 실패 시 가입 RPC 미호출
- 가입 RPC 실패 시 같은 업로드 경로 재사용
- 가입 성공 후 사진 단계를 다시 요구하지 않음
- 기존 null/legacy 사진 사용자의 로그인은 차단하지 않음
- 사진 교체는 새 객체 업로드 → DB 포인터 변경 → 이전 객체 삭제
- DB 변경 성공 후 객체 삭제만 실패한 경우 orphan으로 분리
- 계정 전환·로그아웃 시 signed URL 캐시 초기화
- 기존 `http:`, `https:`, `data:` 사진 값은 이번 배포에서 파괴적으로 변환하지 않음

## 7. Supabase Expansion 적용

이 단계부터는 사용자 인터뷰가 종료됐고 이 프롬프트를 실행하라는 사용자의 지시를 원격 적용 승인으로 사용합니다. 다만 아래 중단 조건을 반드시 지키세요.

적용 직전:

- MCP 서버 project ref 재확인
- 원격 migration history 재확인
- Storage bucket·policy 이름 충돌 확인
- 관련 RPC signature와 권한 재확인
- Auth 사용자, 프로필, 공고 수와 기존 주요 공고 ID/제목 기준값 기록
- 원격 배포 상태와 Vercel Production URL 기록

다음 조건이면 원격 변경 없이 중단하세요.

- project ref 불일치
- 로컬 migration version이 이미 다른 내용으로 적용됨
- 예상하지 못한 `profile-images` bucket 또는 동명 policy/RPC 존재
- 기존 데이터 수가 작업 시작 후 설명 없이 급변
- 마이그레이션이 기존 Vercel의 로그인·공고 조회·기존 가입 RPC를 즉시 깨뜨리는 구조

조건이 맞으면 **Expansion 마이그레이션만** 정확한 프로젝트에 적용하세요.

- private bucket과 최소 권한 policy
- 사진 객체 검증 함수
- 버전된 `complete_signup_with_avatar`
- 사진 변경·삭제 RPC
- 직접 `avatar_url` 변경 우회 차단
- 기존 `complete_signup(...)`은 이 단계에서 유지

마이그레이션을 여러 번 임의 SQL로 고치지 마세요. 적용이 실패하면 오류와 현재 transaction 상태를 확인하고, 부분 적용 여부를 읽기 전용으로 진단한 뒤 안전한 후속 마이그레이션이 필요한지 판단하세요.

## 10. 실제 Production 스모크 테스트

새 배포가 준비된 뒤 모바일 크기와 일반 브라우저에서 확인하세요.

### 비변경·기존 흐름

- 비로그인 공고 목록·상세
- 기존 회원 로그인
- 작성자 성별·만 나이
- 기존 공고·신청·채팅 주요 조회
- 기존 null/legacy 사진 표시

### 프로필 사진 흐름

- 사진 없는 가입 완료 거부
- 정상 사진 선택·미리보기·재선택
- 허용되지 않는 파일과 손상 파일 거부
- 사진 업로드 후 신규 가입 완료
- 저장된 DB 값이 stable object path인지 확인
- signed URL 표시와 새로고침 후 재표시
- 본인 사진 변경
- 본인 사진 삭제 후 로그인 유지
- 타인 경로 업로드·교체·삭제 거부
- anonymous 사진 읽기 거부
- 가입 RPC 실패·재시도 시 중복 프로필과 불필요한 재업로드 없음

실제 신규 가입 검증에는 RUNBOOK에서 허용한 폐기 가능한 통제 테스트 번호만 사용하세요. 허용된 번호가 없으면 기존 데이터를 임의로 재사용하거나 새 실사용자 번호를 만들지 말고 해당 테스트를 `BLOCKED`로 기록하세요. 테스트로 생성한 계정·프로필·객체를 삭제해야 한다면 기존 데이터와 정확히 구분하고, 프로젝트의 승인된 정리 절차만 사용하세요.

Production 테스트 중 기존 실제 데이터를 수정·삭제하지 마세요. 기존 사용자 행을 테스트 대상으로 삼아 사진을 바꾸지 마세요.

## 11. 기존 사진 없는 가입 경로 차단

새 Vercel 배포와 사진 가입 흐름이 실제로 통과한 경우에만 별도 **Contraction 마이그레이션**을 생성·적용하세요.

- 일반 `authenticated`의 기존 `complete_signup(text,date,text,text,text)` 실행 권한 회수
- 새 `complete_signup_with_avatar`만 신규 가입 완료에 사용
- direct `profiles` insert와 direct `avatar_url` update가 계속 거부되는지 확인
- 기존 가입 완료 회원의 로그인·조회·프로필 편집은 유지
- service role 등 실제 운영에 필요한 호출 주체를 무분별하게 차단하지 않음

다음 조건이면 Contraction을 적용하지 마세요.

- Vercel에 구버전 배포가 아직 트래픽을 받음
- 신규 사진 가입 스모크가 실패 또는 미실행
- 새 RPC 오류가 남음
- 롤백 가능 상태가 확인되지 않음

Contraction 적용 후 최종 권한 테스트와 기존 회원 회귀 테스트를 다시 수행하세요. 생성된 후속 마이그레이션 파일도 Git에 커밋·push하고 해당 Vercel 배포가 성공했는지 확인하세요.

## 12. 개인정보와 Storage 읽기 범위

현재 설계는 authenticated 회원 전체가 `profile-images` bucket 객체를 SELECT할 수 있어 클라이언트가 signed URL을 만들 수 있습니다. 이는 비로그인 공개는 아니지만 객체 목록 접근 범위가 넓다는 제한이 있습니다.

- 이번 인터뷰 개선사항에서 더 좁은 사진 공개 범위를 확정하지 않았다면, 임의로 복잡한 Edge Function을 추가하지 말고 이 제한을 운영 위험으로 유지·기록하세요.
- 실제 정책이 `로그인 회원 전체에게 프로필 사진 공개`라면 그 근거를 문서화하세요.
- 실제 정책이 `공고·신청·동행 관계가 있는 사용자에게만 공개`라면 현재 SELECT policy로 배포하지 말고 권한 계약을 먼저 구현·검증하세요.
- private bucket이라는 이유만으로 모든 로그인 회원 사이에서도 비공개라고 표현하지 마세요.

## 13. 모니터링과 복구

배포 직후 다음을 확인하세요.

- Vercel 함수/브라우저 오류
- Supabase Auth·Storage·Database 관련 오류
- 사진 업로드 실패율과 RPC 오류
- 기존 로그인 및 공고 조회 회귀
- 예상보다 많은 orphan 객체 발생 여부

오류가 발생하면 범위에 따라 복구하세요.

- 프론트 오류: 직전 Vercel 배포로 롤백, Expansion 객체는 기존 앱과 호환되므로 유지
- 권한 과다: 프론트 롤백 후 권한을 좁히는 후속 마이그레이션
- 신규 가입 오류: Contraction 미적용 또는 기존 RPC 권한을 제한적으로 복구하고 원인 수정
- 데이터 이상: 삭제·보정하지 말고 즉시 쓰기를 멈춘 뒤 읽기 전용으로 진단

orphan 정리는 이번 즉시 배포 성공 조건이 아닙니다. 참조되지 않고 생성 후 24시간 이상 지난 `<uuid>/<uuid>.jpg`만 dry-run으로 식별한 뒤 별도 운영 작업으로 정리하세요. `storage.objects`를 직접 SQL DELETE하지 말고 Storage API를 사용하세요.
