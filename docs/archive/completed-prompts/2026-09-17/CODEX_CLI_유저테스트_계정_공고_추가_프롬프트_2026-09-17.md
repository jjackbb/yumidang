중복 방지를 위해 다음 순서로 처리하세요.

1. Auth Admin API의 사용자 조회로 해당 전화번호가 이미 존재하는지 확인하세요. 전화번호 전체를 로그에 출력하지 마세요.
2. 이미 존재하면 그 Auth UUID를 재사용하고 새 계정을 추가로 만들지 마세요.
3. 없다면 공식 `auth.admin.createUser`로 생성하고 `phone_confirm: true`를 설정하세요.
4. 같은 UUID의 `public.profiles`를 확인하세요. 없으면 생성하고, 있으면 위 테스트 계정의 실명·성별·생년월일·자기소개가 일치하도록 해당 프로필만 수정하세요.
5. 프로필 사진은 기존 서비스의 중립적인 기본/테스트 아바타가 있으면 사용하세요. 실제 인물의 사진처럼 보이는 이미지를 새로 만들지 마세요. 적절한 자산이 없고 DB에서 선택 사항이면 `null`로 두세요.
6. 다른 사용자의 계정이나 프로필은 변경하지 마세요.

이 번호가 Supabase Auth의 통제된 테스트 전화번호로 등록되어 있다면 기존 고정 OTP 흐름으로 로그인까지 검증하세요. 등록되어 있지 않으면 실제 SMS를 보내지 말고 다음 중 가능한 방식으로 처리하세요.

- 현재 권한으로 공식 Auth 테스트 전화번호 설정을 안전하게 추가할 수 있으면 그렇게 설정
- 설정 권한이 없다면 계정과 공고 생성은 완료하되 로그인 검증은 `BLOCKED`로 기록하고, 사용자가 Dashboard에서 해야 할 메뉴와 값만 정확히 알려 주기

고정 OTP 값은 터미널 출력이나 보고서에 남기지 마세요. `phone_confirm: true`만으로 OTP 로그인이 검증된 것처럼 보고하지 마세요.

## 3. 검증

데이터를 더 만들지 않는 읽기 중심 검증을 수행하세요.

1. 기존 Auth 사용자와 기존 사용자 데이터의 개수가 작업 전보다 줄지 않았는지 확인
2. 지정 전화번호의 Auth 사용자가 정확히 1명인지 확인
3. 그 UUID의 프로필 값이 지정 내용과 일치하는지 확인
4. 위 계정의 활성 공고 6개가 중복 없이 존재하는지 확인
5. 공고 6개가 공개 목록에 표시되고 검색·카테고리 필터 대상이 되는지 확인
6. 비공개 정확한 장소가 공개 목록이나 비로그인 응답에 노출되지 않는지 확인
7. 가능하면 실제 SMS 없이 브라우저에서 로그인하고 내 공고 목록과 상세를 확인

기존 전체 자동화 하네스는 계정과 공고를 추가하거나 바꿀 수 있으므로 실행하지 마세요. 검증 때문에 생성한 임시 데이터가 있다면 이번 계정과 공고 6개를 제외한 **임시 데이터만** 정리하세요. 기존 데이터는 정리 대상이 아닙니다.
