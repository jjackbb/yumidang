## 사용자 확정 정책 — 이 내용이 이전 코드·테스트보다 우선

### P1. 철회 후 재신청

- 신청자가 자신의 `pending` 신청을 철회한 경우, 공고가 여전히 신청 가능한 상태라면 같은 공고에 다시 신청할 수 있다.
- 재신청은 철회된 행을 되살리지 않고 반드시 새로운 `request_id`와 새 `created_at`을 만든다.
- 이전 신청, 상태 변경 이력, 이전 채팅 기록은 보존한다. 철회된 이전 대화방은 읽기 전용이고, 새 신청은 새 대화방을 사용한다.
- 동일 사용자의 현재 `pending` 신청이 이미 있으면 중복 신청을 만들지 않는다. 동시 재신청도 활성 신청 1개만 생성되어야 한다.
- 작성자가 `declined`로 거절한 이력이 같은 공고에 하나라도 있으면 해당 신청자는 그 공고에 재신청할 수 없다. 일반 오류로 숨기지 말고 UI에서 이해할 수 있는 안정적인 오류 코드를 반환한다.
- `matched` 상태이거나 다른 신청자가 선택되어 공고가 닫힌 경우 등 기존 신청 불가 조건은 유지한다.
- `(post_id, requester_id)` 전체 UNIQUE로 새 이력 행을 막는 현재 구조를 정책에 맞게 교체하되, 과거 행을 삭제하거나 ID를 재사용하지 않는다. 적용된 과거 migration 파일을 고치지 말고 새 append-only migration을 만든다.

### P2. 수동 완료·자동완료·이의제기

- 요청자와 작성자 모두 **동행 예상 종료 시각 `ends_at` 이후에만** 완료 처리할 수 있다. 시작 이후가 아니다.
- 예상 종료 전에는 UI 버튼을 비활성화하고, 서버 RPC도 반드시 `too_early` 등 안정적인 오류로 거부한다. 클라이언트 시각을 신뢰하지 않는다.
- 어느 한쪽이 완료 처리하면 두 번째 확인을 기다리지 않고 동행을 완료 상태로 전환한다. 누가 수동 처리했는지와 서버 완료 시각을 감사 가능하게 보존한다.
- 같은 사람의 재시도와 양쪽의 동시 완료 요청은 멱등적이어야 한다. 완료 행·알림·후속 처리를 중복 생성하지 않는다.
- 아무도 수동 완료하지 않으면 `ends_at + 24시간`에 서버가 자동완료한다.
- 취소·불발·이미 분쟁 중인 동행은 자동완료 대상에서 제외한다. 현재 저장소에 이 상태가 아직 없다면 존재하는 것처럼 가장하지 말고, 이번 기능에 필요한 최소 상태/계약을 추가하거나 명확한 후속 통합 지점을 남겨라.
- 자동완료는 조회가 발생했을 때만 뒤늦게 상태를 바꾸는 lazy update를 ‘자동완료 완료’로 표현하면 안 된다. 현재 허용된 Supabase 환경에서 실제 예약 실행(pg_cron 등) 가능 여부를 확인하고 구현·적용·검증해. 권한 때문에 예약 실행을 적용할 수 없으면 due 처리 함수와 안전한 멱등 계약까지 구현하되, 예약 적용은 BLOCKED/NOT_RUN으로 정확히 기록하고 사용자에게 필요한 한 단계만 알려라.
- 수동 완료라면 완료하지 않은 상대방, 자동완료라면 양쪽 모두가 이의를 제기할 수 있다.
- 완료 알림을 앱에서 확인 가능한 상태로 만든 서버 시각을 기록하고, 그 시각부터 24시간을 이의제기 기한으로 사용한다. 단순 푸시 수신이나 실제 열람 시각으로 추정하지 않는다.
- 완료 직후 상태는 완료로 표시할 수 있지만, 24시간 동안 해당 동행의 평가 공개·당도 반영·유효 완료 횟수 반영은 보류한다.
- 이의가 접수되면 해당 동행만 운영 판정까지 계속 보류한다. 다른 동행과 계정 전체를 함께 막지 않는다.
- 이의제기 기간 뒤에도 일반 신고·고객지원은 가능하다는 정책을 훼손하지 않는다.
- 운영자 판정 UI 전체를 새로 만드는 것이 범위를 크게 벗어나면 임의의 일반 사용자에게 판정 권한을 주지 마. 안전한 데이터 상태와 비공개 운영 계약을 만들고, 실제 관리 권한·도구가 없으면 그 실행 검증을 NOT_RUN으로 표시해.

### P3. 평가기간·블라인드 공개

- 평가 작성 기간은 `completed_at`부터 7일이다. 기존처럼 `ends_at + 7일`로 계산하지 않는다.
- 완료된 동행의 요청자와 작성자는 각각 한 번만 평가할 수 있다. 기존 별점 범위, 선택 후기, 제출 후 수정 불가, 원본 테이블 직접 접근 차단은 유지한다.
- 완료 후 첫 24시간 이의제기 기간에는 평가를 작성할 수는 있지만 상대 평가 내용, 당도 변화, 유효 완료 횟수는 공개/반영하지 않는다.
- 이의제기가 없고 24시간 보류가 끝난 뒤:
  1. 양쪽이 모두 제출했다면 즉시 서로의 평가를 공개한다.
  2. 한쪽만 제출했다면 7일 기한까지 계속 블라인드로 유지하고, 기한이 끝나면 제출된 평가만 공개한다. 제출하지 않은 쪽은 기한 후 작성할 수 없다.
  3. 아무도 제출하지 않았다면 공개할 평가는 없다.
- 평가 공개 자격은 서버 시각으로 계산하여, 기한 경과 후 별도 배치가 없어도 안전하게 조회 결과에 반영될 수 있다.
- 이의제기/분쟁이 접수되면 평가 작성 기한의 남은 시간을 보존하고 평가 공개를 중지한다.
- 운영자가 실제 동행으로 인정하면 남은 기간을 재개하되, 미제출자에게 최소 24시간을 보장한다. 양쪽이 이미 제출했다면 판정 및 24시간 이의 보류 조건이 해소된 뒤 공개할 수 있다.
- 불발로 판정하면 일반 상호평가·당도·유효 완료 횟수에서 제외한다.
- Q15와 Q19는 아직 미확정이다. 별점/후기 점수 산식이나 최종 당도 갱신 방식을 임의로 정하지 마. 이번 범위에서는 이의제기·분쟁 중 당도를 반영하지 않는 계약만 보장하고, 실제 당도 계산이 아직 없다면 새 산식을 만들지 마.

## 반드시 검증할 시나리오

### 재신청

1. 신청 → 본인 철회 → 이전 행/채팅 보존 → 새 `request_id`로 재신청.
2. 재신청 뒤에는 새 채팅만 쓰기 가능하고 이전 철회 채팅은 읽기 전용.
3. pending 상태에서 반복 클릭·동시 요청은 활성 행 하나만 유지.
4. 작성자 거절 뒤 같은 공고 재신청 거부.
5. 제3자·익명 사용자의 신청/이력/대화 접근 거부.

### 완료·이의제기

1. 요청자와 작성자 모두 `ends_at` 직전 완료 거부, 경계 시각부터 허용.
2. 어느 한쪽의 수동 완료만으로 완료 전환되고 상대의 두 번째 확인이 필요하지 않음.
3. 반복/동시 요청의 멱등성과 서버 타임스탬프·완료 주체 기록.
4. 미처리 건은 `ends_at+24h` 자동완료, 취소·불발·분쟁 건은 제외.
5. 수동 완료의 상대방 및 자동완료의 양쪽만 24시간 안에 이의제기 가능. 익명·제3자·기한 후 요청 거부.
6. 이의제기 동안 해당 동행의 평가 공개·당도·유효 완료 집계만 보류.

### 평가

1. `completed_at` 이전 제출 거부, 완료 후 작성 가능, `completed_at+7d` 경계에서 마감.
2. 양쪽 제출이 24시간 이의제기 기간 안에 끝나도 상대 내용은 숨김. 보류 종료 후 공개.
3. 한쪽만 제출하면 7일 전까지 숨김, 정확히 기한 종료 후 상대에게 공개.
4. 기한 종료 뒤 미제출자는 작성 불가.
5. 분쟁 접수 즉시 작성 시계와 공개 정지. 실제 동행 인정 시 남은 기간 또는 최소 24시간, 불발 확정 시 제외.
6. 평가 원본은 브라우저 직접 SELECT/INSERT/Realtime으로 유출되지 않고 RPC도 참여자에게 필요한 필드만 반환.

## 문서화와 종료 조건

- 새 정책을 노션에 직접 반영하는 것은 이번 코드 작업 범위가 아니다. 로컬 질문지에는 결정이 기록되어 있으므로 코드와 충돌하면 이 프롬프트가 우선한다.
- 실제 SMS 인증, 실제 사용자 검증, Gemini 독립 검증을 수행한 것으로 표현하지 마.
- commit, push, PR, 배포는 하지 마.
- 완료 보고에는 변경 파일, 원격 적용 migration, 테스트별 실제 결과와 run ID, 남은 NOT_RUN/BLOCKED, 정책과 구현이 정확히 일치하는지를 간결하게 적어.
