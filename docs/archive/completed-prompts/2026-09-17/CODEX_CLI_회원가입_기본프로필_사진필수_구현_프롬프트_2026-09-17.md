## 4. 기본 프로필 UI

기존 회원가입 모달의 디자인 체계와 모바일 레이아웃을 유지하면서 `기본 프로필 입력`에 사진 입력을 추가하세요.

- 입력 순서의 첫 부분에 원형 사진 미리보기와 `프로필 사진 (필수)` 라벨 표시
- 최초 상태에는 기본 아이콘과 `사진 선택` 버튼 표시
- 선택 후에는 미리보기, `다시 선택` 버튼 제공
- 허용 원본: JPG, JPEG, PNG
- 원본 파일 최대 크기: 10MB
- 빈 파일, 손상되어 디코딩할 수 없는 파일, 허용되지 않은 형식은 거부
- 기존 이미지 리사이즈 유틸리티를 재사용하거나 안전하게 개선해 긴 변 기준 최대 480px, JPEG 품질 0.82 수준으로 변환
- 업로드할 파일과 미리보기 URL의 생명주기를 분리하고, 사용하지 않는 object URL은 해제
- 사진이 없거나 검증에 실패한 동안 다음/가입 완료 버튼 비활성화
- 키보드 조작, 접근 가능한 라벨, 포커스 이동, 오류 메시지 연결 유지
- 업로드 중 중복 제출 방지 및 진행 상태 표시
- 네트워크 오류, 권한 오류, 업로드 실패, 가입 완료 실패에 각각 재시도 가능한 일반 사용자 문구 제공

여성 사용자는 기본정보 제출 후 가입 완료 과정에서 사진을 업로드합니다. 남성 사용자는 추천 코드 또는 학교·직장 이메일 자격 확인이 끝난 뒤 최종 가입 완료 과정에서 사진을 업로드합니다. 자격 확인 전 사진 원본을 서버에 미리 남길 필요는 없습니다. 앞 단계와 뒤로 가기를 오가더라도 같은 모달 세션에서는 선택한 사진과 미리보기를 가능한 한 유지하세요.

페이지 새로고침 뒤 로컬 파일 선택은 복원할 수 없으므로, 사진이 아직 서버에 저장되지 않았다면 `프로필 사진을 다시 선택해 주세요`라고 안내하세요. 브라우저 저장소에 이미지 Base64를 보관하지 마세요.

## 5. Supabase Storage 계약

DB에 Base64 data URL이나 이미지 바이너리를 저장하지 마세요. private Supabase Storage bucket을 사용하세요.

권장 계약은 다음과 같습니다. 기존 저장 구조가 있다면 같은 보안 수준을 만족하도록 이름만 조정할 수 있습니다.

- private bucket 이름: `profile-images`
- 저장 파일은 리사이즈된 JPEG만 허용
- 최종 객체 경로: `<auth.uid()>/avatar.jpg` 또는 충돌과 캐시 갱신을 안전하게 처리하는 동등한 사용자 소유 경로
- `profiles.avatar_url`에는 만료되는 signed URL이 아니라 안정적인 Storage object path를 저장
- 기존 `http://`, `https://`, `data:` 값이 존재한다면 즉시 파괴적으로 변환하지 말고 호환 처리와 향후 정리 방식을 문서화
- UI 표시 시 중앙화된 이미지 resolver가 private object path를 짧은 만료 시간의 signed URL로 바꿔 사용
- signed URL 자체를 DB에 저장하지 않음
- 비로그인 사용자는 bucket 객체를 읽을 수 없음
- 로그인 사용자는 서비스에서 필요한 다른 회원의 프로필 사진을 읽을 수 있음
- 쓰기·교체·삭제는 경로 첫 폴더가 `auth.uid()`인 본인 객체에만 허용
- 다른 사용자의 경로를 업로드, 교체, 삭제할 수 없음
- upsert를 쓴다면 Supabase Storage에 필요한 `INSERT`, `SELECT`, `UPDATE` 권한을 모두 검증
- 허용 MIME과 최대 업로드 크기를 bucket 설정에서도 제한

Storage bucket과 `storage.objects` 정책은 새 마이그레이션으로 관리하되, 현재 Supabase 공식 권장 방식과 원격 상태를 먼저 확인하세요. 정책 이름 충돌이나 기존 bucket 존재 여부를 숨기는 무분별한 `if exists` 처리는 피하세요.

## 6. 가입 완료 서버 계약

앞선 프롬프트의 서버 검증형 가입 완료 RPC에 사진 조건을 통합하세요. 클라이언트가 `avatar_url` 문자열만 보내면 통과시키는 방식은 금지합니다.

가입 완료 순서:

1. 클라이언트에서 파일 형식·크기·디코딩 가능 여부 확인
2. 리사이즈된 JPEG Blob 생성
3. 현재 인증 사용자의 소유 경로로 private bucket에 업로드
4. 가입 완료 RPC에 stable object path 전달
5. 서버가 `auth.uid()` 존재, 경로 형식, 해당 bucket의 객체 존재, 현재 사용자 소유를 직접 확인
6. 성별별 가입 자격과 기본정보를 함께 검증
7. 프로필과 가입 관련 데이터를 하나의 트랜잭션으로 생성

RPC는 다음을 보장해야 합니다.

- 사진 경로가 없거나 공백이면 거부
- 존재하지 않는 객체면 거부
- 다른 사용자의 객체 경로면 거부
- 프로필 생성 실패 시 일부 가입 데이터가 남지 않음
- 같은 사용자가 재시도해도 프로필·추천 기록 등이 중복되지 않는 멱등 처리
- 가입 완료 응답에 signed URL이나 민감한 내부 Storage 정보를 과도하게 포함하지 않음
- `SECURITY DEFINER`가 꼭 필요하다면 비노출 스키마, 고정 `search_path`, 함수 내부 `auth.uid()` 검사, `PUBLIC` 실행 권한 회수, 필요한 역할에만 명시적 `GRANT` 적용
- 일반 사용자가 `profiles` 직접 insert로 사진·가입 자격 검증을 우회할 수 없음

기존 프로필이 `avatar_url = null`일 수 있으므로 즉시 전역 `NOT NULL`을 걸어 원격 적용을 실패시키지 마세요. **신규 가입 완료 RPC에서 필수 조건을 강제**하고, 기존 사용자는 소급 차단하지 않는 호환 전략을 사용하세요.

업로드 후 RPC가 일시 실패했을 때 같은 사용자가 같은 사진으로 안전하게 재시도할 수 있어야 합니다. 가입을 끝내지 않고 떠난 사용자의 고아 객체가 생길 수 있으므로, 무기한 쌓이지 않는 정리 기준을 문서화하고 가능한 범위에서 구현하세요. 단, 정리 작업이 정상 가입자의 현재 사진을 삭제해서는 안 됩니다.

## 7. 프로필 편집과 이미지 표시

- `ProfileEditor`가 data URL을 `profiles.avatar_url`에 직접 저장한다면 동일한 Storage 업로드 계약으로 교체
- 사진 변경 성공 후 새 이미지를 즉시 표시하고 캐시 때문에 이전 이미지가 남지 않게 처리
- 변경 실패 시 기존 정상 사진과 DB 경로를 유지
- 사진 삭제 시 본인 객체와 프로필 경로를 일관되게 처리하고, 실패 중간 상태를 만들지 않음
- 기존 null 사진 사용자는 프로필 편집에서 사진을 등록할 수 있음
- 가입 때 사진이 저장된 신규 사용자는 가입 후 프로필 설정의 사진 단계가 완료된 것으로 판단하고 관심사·소개 등 다음 미완성 단계부터 시작
- 앱의 작성자 카드, 상대 프로필, 내 프로필 등 기존 `avatar_url` 소비 지점을 조사해 private Storage 경로를 `<img src>`에 직접 넣지 말고 중앙 resolver를 사용
- 로그아웃이나 계정 전환 시 이전 사용자의 signed URL과 사진 상태가 새 사용자 화면에 남지 않게 정리

- 현재 원격 migration history, `profiles` 계약, Storage bucket과 정책은 필요할 때 읽기 전용으로만 조회하세요.
- 새 마이그레이션은 파일로만 작성하고 원격 프로젝트에 적용하지 마세요. `execute_sql`로 시험 적용하는 것도 금지합니다.
- 로컬 Supabase 환경이 이미 안전하게 준비돼 있다면 로컬 DB에서만 마이그레이션을 검증할 수 있습니다. 로컬 환경이 없거나 Docker 실행이 불가능하면 SQL 정적 검토와 mock 테스트까지만 수행하고 `NOT_RUN`으로 기록하세요. 원격 프로젝트를 대체 테스트 환경으로 사용하지 마세요.
- `.env`가 원격 Supabase를 가리킬 수 있으므로 개발 서버와 브라우저 테스트가 실제 가입, 업로드, 프로필 변경을 보내지 않는지 먼저 확인하세요. 원격 쓰기 가능성이 있으면 mock adapter 또는 로컬 Supabase로 격리하세요.
- 기존 사용자 프로필의 `avatar_url` 값을 임의로 변경하거나 테스트용 사진을 주입하지 마세요.
- 원격 검증용 임시 Auth 사용자, 프로필, Storage 객체를 만들지 마세요.
- Database와 Security advisor는 읽기 전용 실행이 가능하면 현재 기준 결과를 확인할 수 있지만, 이번 변경은 미적용 상태이므로 원격 advisor 통과를 새 변경의 검증 근거로 표현하지 마세요.

### 향후 배포를 위한 무중단 전환 순서

현재 Production이 기존 가입 계약을 사용하므로, 나중에 사용자가 원격 적용과 배포를 별도로 지시할 때 사용할 정확한 전환 절차를 문서로 남기세요.

1. 기존 Vercel 버전을 깨지 않는 확장형 Storage bucket·policy·신규 또는 호환 RPC 적용
2. 원격 권한과 기존 로그인·공고 조회 스모크 테스트
3. 새 프론트엔드 Vercel 배포
4. 새 회원가입과 사진 업로드 스모크 테스트
5. 기존 사진 없는 가입 우회 경로와 불필요한 이전 RPC 권한 차단
6. 기존 계정 로그인과 유저테스트 공고 6개 보존 재확인

기존 RPC를 즉시 파괴적으로 교체해 구버전 Vercel이 실패하는 설계를 피하세요. 필요하면 버전이 구분된 신규 RPC 또는 하위 호환 인자를 사용하고, 마지막 차단 단계까지 포함해 우회가 영구히 남지 않게 계획하세요. 이 절차는 작성만 하고 이번 작업에서 실행하지 마세요.

## 9. 필수 검증

구현을 그대로 따라 쓰는 테스트보다 권한과 실패 경계를 검증하세요.

### UI와 파일 처리

- 사진 없이 신규 가입 완료 불가
- 정상 JPG/PNG 선택, 미리보기, 다시 선택
- 10MB 초과, 잘못된 MIME, 빈 파일, 디코딩 실패 거부
- 리사이즈 결과가 최대 480px 범위와 JPEG 출력 계약을 만족
- 업로드 중 중복 제출 방지
- 업로드 실패 시 프로필이 생성되지 않고 재시도 가능
- 가입 완료 실패 후 사진을 다시 안전하게 사용할 수 있음
- 가입 성공 후 사진을 다시 요구하지 않고 다음 프로필 항목으로 진행

### Storage와 서버 권한

- mock 또는 로컬 Supabase에서 anon은 사진 객체 읽기·쓰기 불가
- mock 또는 로컬 Supabase에서 로그인 사용자는 서비스에 필요한 프로필 사진 읽기 가능
- mock 또는 로컬 Supabase에서 사용자는 본인 경로만 업로드·교체·삭제 가능
- mock 또는 로컬 Supabase에서 다른 사용자의 경로를 조작할 수 없음
- mock 또는 로컬 Supabase에서 가입 완료 RPC는 빈 경로, 존재하지 않는 경로, 타인 소유 경로를 모두 거부
- mock 또는 로컬 Supabase에서 유효한 본인 객체와 가입 자격을 함께 만족할 때만 프로필 생성
- DB에 Base64나 만료 signed URL이 저장되지 않음
- direct `profiles` insert로 우회 불가

### 회귀 검사

- 기존 사용자 로그인은 사진 null 여부와 무관하게 가능
- 기존 프로필 편집, 프로필 완성 제한, 공고 작성·신청 흐름이 의도대로 유지
- 앞선 성별별 가입 자격 정책과 작성자 성별·만 나이 기능 유지
- 원격에는 쓰지 않았음을 작업 로그로 확인하고, 기존 사용자·프로필·공고 수는 읽기 전용 조회가 필요할 때만 확인
- `npm run lint`
- `npm test`
- `npm run build`
- 데이터 비변경 preflight가 안전함을 확인한 뒤 `npm run harness:preflight`

브라우저 자동화가 가능하면 mock 또는 로컬 Supabase에 격리된 환경에서 모바일 여성 직접 가입 경로와 남성 자격 확인 경로를 각각 점검하세요. 원격 프로젝트를 가리키는 Production 또는 개발 환경에서 실제 가입·사진 업로드 테스트를 하지 마세요. 실제 전화번호 인증 문자나 실제 학교·직장 이메일 발송을 성공했다고 주장하지 말고, 통제된 테스트 인증과 실제 외부 인증을 구분해 보고하세요.
