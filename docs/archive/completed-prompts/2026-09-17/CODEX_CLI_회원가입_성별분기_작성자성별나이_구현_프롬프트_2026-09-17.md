## 4. 가입 흐름 UI

기존 로그인과 회원가입 분리, 약관, 휴대폰 인증, 미완성 프로필 복구 흐름을 유지합니다. 전체 디자인을 바꾸지 말고 현재 모달 안에 조건부 단계를 추가하세요.

### 공통 흐름

`약관 → 휴대폰 인증 → 기본정보 입력 → 조건부 가입 자격 확인 → 가입 완료 → 프로필 만들기`

- 기본정보: 실명, 생년월일, 성별
- 성별 선택 전에는 다음 단계로 진행할 수 없음
- 여성 선택 시 자격 확인 화면을 건너뛰고 서버에서 가입 완료
- 남성 선택 시 `가입 자격 확인` 화면 표시
- 남성 화면에는 다음 두 선택지를 라디오 또는 카드 형태로 제공
  - `여성회원 추천 코드`
  - `학교·직장 이메일`
- 선택한 방법의 입력란만 표시
- 뒤로 가면 입력한 기본정보를 유지
- 요청 중 중복 클릭을 막고 로딩·오류·재시도 상태 제공
- 새로고침이나 모달 재진입 시 휴대폰 세션이 살아 있지만 프로필이 없으면 회원가입 미완성 상태로 이어갈 수 있어야 함
- 가입 완료 전에는 공고 작성·신청·채팅을 사용할 수 없음

### 여성회원 추천 코드

- 형식 예시: `YMD-12AB34CD`. 대문자·숫자·하이픈만 사용하고 충분히 무작위로 생성
- 사용자가 소문자로 입력해도 서버에서 대문자로 정규화
- 유효하지 않은 코드에는 여성회원 존재 여부를 추측할 수 없는 일반 오류 제공
- 남성 본인의 가입 완료 시 서버가 코드 소유자가 가입 완료된 여성 프로필인지 검증
- 재사용 가능 정책이므로 사용 후 코드를 비활성화하거나 소모하지 않음
- 어느 남성이 어떤 코드로 가입했는지는 공개하지 않되 서버 감사용 연결 기록을 유지
- 추천 코드 자체와 추천 관계를 공개 프로필, 공고, 상대 프로필 API에 포함하지 않음

- 잘못된 코드, 만료, 무료 메일, 이미 사용된 이메일, 서버 오류를 구분해 이해하기 쉬운 메시지 제공

## 5. 여성회원의 재사용 추천 코드 UI

여성 가입이 완료되면 서버가 여성회원별 고유 추천 코드 하나를 생성합니다.

- 여성회원 본인의 Me/프로필 영역에만 `내 추천 코드` 카드 표시
- 코드 복사 버튼과 `유저테스트에서는 여러 번 사용할 수 있어요` 안내 제공
- 남성 및 비로그인 사용자에게는 이 카드와 코드를 노출하지 않음
- 기존 여성회원에게 코드가 없다면 본인이 화면을 열었을 때 안전한 서버 RPC로 한 번만 생성
- 동시에 여러 요청이 와도 코드가 하나만 생성되도록 DB 고유 제약과 원자적 처리를 사용
- 추천 코드 조회/생성 RPC는 본인의 성별을 서버에서 검사

## 6. 서버·데이터 계약

구체적인 이름은 기존 규칙에 맞춰 조정할 수 있지만 아래 책임을 분리해 구현하세요.

### 가입 자격 데이터

- 여성회원별 추천 코드 테이블
  - 코드 고유
  - 여성 소유자당 활성 코드 1개
  - 소유자 프로필과 FK 연결
- 추천 가입 기록
  - 추천받은 남성 사용자당 1개
  - 추천한 여성 사용자와 연결
  - 생성 시각 기록
- 학교·직장 이메일 인증 상태
  - Auth 사용자 UUID
  - 정규화된 이메일
  - 요청/확인/만료 시각
  - 인증 완료 여부
  - 한 이메일은 한 사용자만 가입 완료에 사용 가능
- 가입 경로 기록
  - `female_direct`, `female_referral`, `institutional_email`, 기존 계정용 `legacy`
  - 일반 사용자가 다른 사용자의 가입 경로를 조회할 수 없게 보호

정확한 이메일·추천 코드·추천 관계 테이블은 RLS를 활성화하고 기본적으로 `anon`, `authenticated`의 직접 읽기/쓰기를 차단하세요. 필요한 동작만 최소 권한의 RPC/Edge Function으로 제공합니다.

### 가입 완료 서버 명령

현재 `AuthModal`이 `profiles`에 직접 `insert`하는 구조를 서버 검증형 가입 완료 RPC로 교체하세요.

RPC는 다음을 보장해야 합니다.

- `auth.uid()`가 반드시 존재
- 이미 프로필이 있으면 중복 생성하지 않는 멱등 처리
- 실명·생년월일·만 19세·성별을 서버에서도 검증
- 여성은 추가 증명 없이 프로필 생성 및 추천 코드 생성
- 남성 추천 경로는 유효한 여성 소유 추천 코드를 서버에서 확인
- 남성 이메일 경로는 현재 사용자에게 연결된 미만료 서버 인증 상태 확인
- 프로필 생성, 가입 경로 기록, 추천 기록/이메일 연결을 하나의 트랜잭션으로 처리
- 클라이언트가 `gender=female`로 보낸 값은 자기기입 값일 뿐이라는 한계를 유지하되, 선택한 값에 맞는 서버 분기를 일관되게 적용
- 실패하면 프로필이 일부만 생기지 않음
- 재시도 시 같은 결과를 반환하고 중복 추천 기록을 만들지 않음

일반 `authenticated` 사용자가 `profiles`에 직접 행을 삽입해 남성 자격 확인을 우회할 수 없도록 권한과 RLS를 조정하세요. 본인 프로필의 허용된 편집 기능은 깨뜨리지 마세요. 기존 가입 완료 계정의 로그인·조회·편집도 유지하세요.

### 테스트 이메일 인증 서버

기존 `test-phone-auth`와 같은 통제 원칙을 따르는 별도 Edge Function 또는 동등한 서버 경계를 사용하세요.

- 대상 프로젝트 ref 고정
- 활성 플래그와 만료 시각 필수
- 인증된 Supabase 사용자만 요청 가능
- 요청/검증 payload 크기와 형식 제한
- 고정 테스트 코드 검증은 서버에서 수행
- 실제 이메일 API 호출 없음
- Secret key는 서버 환경에서만 사용
- 응답에 JWT, Secret, 이메일 원문 등 민감정보를 반환하지 않음
- 반복 시도에 기본적인 제한 적용
- CORS와 오류 메시지는 기존 함수 규칙과 일관되게 처리

기능 이름과 화면 문구에 `test` 또는 `유저테스트`를 명확히 포함해 실제 이메일 인증으로 오해되지 않게 하세요.

프론트엔드:

- `src/live/api.ts`의 타입과 어댑터를 실제 응답에 맞게 갱신
- 공고 상세 작성자 영역에서 `여성 · 만 00세` 또는 `남성 · 만 00세` 표시
- 로그인하지 않은 상태에서는 성별·만 나이를 보여주지 않고 RPC도 호출하지 않음
- 로딩·오류 상태에서 개인정보를 추측해 표시하지 않음
- 생년월일 원문을 클라이언트 상태나 공개 객체로 복사하지 않음
- 현재 모바일 모달 레이아웃과 접근 가능한 라벨/포커스 흐름 유지

## 8. 마이그레이션과 원격 적용

- 기존 마이그레이션 파일을 수정하지 말고 새 타임스탬프 마이그레이션을 추가하세요.
- 현재 원격 스키마와 migration history를 먼저 비교하세요.
- SQL은 재적용 가능한 `if exists` 남용으로 오류를 숨기지 말고, 현재 계약에서 한 단계 앞으로 가는 명확한 마이그레이션으로 작성하세요.
- 로컬 정적 검사와 SQL 검토가 통과한 뒤에만 프로젝트 고정 Supabase MCP로 원격 마이그레이션을 적용하세요.
- Edge Function이 필요하면 로컬 소스와 README를 작성하고 정확한 프로젝트에만 배포하세요.
- 기존 `test-phone-auth` 설정, 만료 시각, Secrets를 변경하지 마세요.
- 원격 적용 전후 Auth 사용자 1, 프로필 1, 공고 6이 유지되는지 확인하세요.

프론트엔드 Production 배포, Git push는 이번 범위가 아닙니다. 로컬에서 원격 백엔드를 연결해 검증하고 배포가 필요한 변경 목록만 보고하세요.

## 9. 테스트

기존 테스트를 수정할 때 과거 정책을 억지로 유지하지 말고 새 확정 정책을 검증하세요. 구현을 그대로 복제하는 무의미한 테스트는 추가하지 마세요.

### 필수 자동 검사

- 기존 `npm run lint`
- 기존 `npm test`
- `npm run build`
- 데이터 비변경 preflight가 안전함을 확인한 뒤 `npm run harness:preflight`

기존 전체 하네스와 기능별 원격 하네스는 테스트 계정을 생성하므로 실행하지 마세요.

### 가입 정책 테스트

- 여성: 휴대폰 세션 + 유효한 기본정보만으로 가입 완료
- 남성: 추천/이메일 증명 없이 가입 완료 거부
- 남성: 존재하지 않는 코드, 남성 소유 코드, 잘못된 형식 거부
- 여성 추천 코드: 여성 본인만 조회, 같은 코드로 서로 다른 남성 가입이 가능한 재사용 정책
- 추천 코드 동시 생성에서도 여성당 1개
- 남성 이메일: 무료 메일 거부, 이메일 변경 시 인증 무효, 잘못된 코드·만료 거부
- 남성 이메일: 올바른 테스트 코드와 미만료 상태에서만 가입 완료
- 동일 이메일의 다른 계정 재사용 거부
- 직접 `profiles` insert로 우회 불가
- 가입 완료 RPC 재시도 멱등
- 기존 가입 계정 로그인·프로필 조회·편집 유지
- 공개 응답에 이메일·추천 코드·추천 관계·가입 경로 없음

### 작성자 정보 테스트

- 로그인 사용자가 공고 상세 작성자의 성별과 서버 계산 만 나이를 봄
- 비로그인 RPC 거부 및 UI 미표시
- 생년월일 원문 미반환
- 삭제/없는 공고의 일반 오류
- 서울 날짜 기준 생일 전날·당일·다음날 만 나이 경계
- 모바일 화면에서 작성자 정보가 잘리지 않고 읽힘

### 실제 브라우저 확인

가능하면 격리된 로컬 Supabase 환경에서 신규 여성/남성 가입 흐름을 실제 브라우저로 확인하세요. 원격 프로젝트에는 테스트 계정을 남기지 마세요.

원격에서는 현재 변종현 계정으로 다음만 확인하세요.

- 기존 전화번호 로그인 유지
- 기존 프로필 추가 인증 요구 없음
- 공고 6개 유지
- 로그인 상태에서 공고 상세 작성자 `남성 · 만 나이` 표시
- 로그아웃 상태에서 작성자 성별·만 나이 미표시

원격 신규 가입 종단 테스트를 수행할 수 없으면 `NOT_RUN`으로 기록하고 로컬/단위/SQL 계약 검증 결과와 구분하세요. 과거 하네스 PASS를 이번 변경의 실측 PASS로 재사용하지 마세요.

테스트 과정에서 원격 임시 계정이나 공고를 만들었다면 완료 전에 반드시 해당 fixture만 정리하고 Auth 사용자 1, 프로필 1, 공고 6으로 복구·검증하세요. 정리 수단을 확보하지 못했다면 처음부터 원격 fixture를 만들지 마세요.

## 10. UX 문구 기준

다음 의미가 사용자에게 분명해야 합니다.

- 여성: `여성 회원은 기본정보 입력 후 바로 가입할 수 있어요.`
- 남성: `여성회원 추천 코드 또는 학교·직장 이메일 확인이 필요해요.`
- 추천 코드: `유저테스트에서는 한 코드를 여러 번 사용할 수 있어요.`
- 이메일: `유저테스트용 인증입니다. 실제 이메일은 발송되지 않아요.`
- 개인정보: `이메일과 추천 정보는 다른 회원에게 공개되지 않아요.`
- 공고 상세: `남성 · 만 30세`와 같이 짧게 표시

여성을 기본값이나 더 우월한 상태처럼 표현하지 말고, 남성에게는 필요한 조건과 해결 방법을 중립적으로 설명하세요. 막힌 상태에서는 무엇을 완료해야 하는지 바로 알 수 있어야 합니다.
