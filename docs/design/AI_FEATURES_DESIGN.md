# AI 기능 설계안 — 후기 브리핑 · 공고 찾기 챗봇

작성: 2026-09-18 · 상태: **설계 초안(구현 전, 승인 필요)**
관련 결정: D-A9(Ai 브리핑 도입, UI 선구현), D-A10(후기 공개 방식 재확인 중)

---

## 0. 한눈에 보기

| 기능 | 하는 일 | 핵심 원칙 |
|---|---|---|
| **Ai 브리핑** | 공개된 후기를 2~3문장으로 요약해 공개 프로필에 표시 | 요약은 **미리 만들어 저장**(조회할 때마다 호출하지 않음) |
| **공고 찾기 챗봇** | "성수에서 조용히 전시 볼 사람" 같은 말로 공고를 찾아줌 | AI는 **검색 조건만** 만들고, 공고 목록은 **DB가 그대로** 내려줌 |

두 기능 모두 **AI 공급자를 바꿔 끼울 수 있는 구조**로 만든다. 테스트는 포텐스닷, 이후 제미나이로 전환한다. 화면과 DB는 공급자를 알지 못한다.

---

## 1. 공통 구조

```
브라우저(React)
   │  (로그인 토큰)
   ▼
Supabase Edge Function  "ai-gateway"
   │  · 요청 검증 · 호출 한도 · 타임아웃 · 로그
   │  · 공급자 어댑터: potens | gemini   ← 환경변수로 전환
   ▼
AI API (포텐스닷 → 제미나이)
```

**왜 서버를 거치나**
1. API 키가 브라우저에 노출되면 누구나 쓸 수 있다. 키는 서버 환경변수로만 둔다.
2. 호출 한도와 비용 상한을 한곳에서 건다.
3. 공급자를 바꿔도 화면 코드를 고치지 않는다.

**공통 안전장치**
- **호출 한도:** 사용자당 분·일 단위 제한, 비로그인은 더 엄격하게. 초과 시 "잠시 후 다시 시도해 주세요".
- **타임아웃:** 8초. 넘으면 AI 없이 동작하는 기본 화면으로 되돌린다.
- **끄는 스위치:** 기능별 on/off 설정값. 문제가 생기면 배포 없이 끈다.
- **로그:** 기능, 소요 시간, 성공 여부, 사용 토큰 수만 남긴다. **후기 원문·검색어 원문은 기본적으로 남기지 않는다**(품질 점검용으로 남기려면 보관 기간과 고지가 필요 → 법률 검토).
- **프롬프트 주입 방어:** 후기·검색어처럼 사용자가 쓴 글은 "지시"가 아니라 "데이터"로 감싸서 보낸다. 모델이 그 안의 명령을 따르지 않도록 시스템 지시에 명시한다.
- **개인정보 최소 전송:** 실명, 전화번호, 생년월일, 이메일, 추천 코드, **확정자 전용 상세 주소**는 절대 보내지 않는다. 마스킹 이름도 보낼 필요가 없다(요약에 이름을 쓰지 않는다).

## 2. 기능 A — Ai 브리핑 (후기 요약)

### 2.1 동작

1. 후기가 새로 공개되면 그 사람의 브리핑을 **오래됨(stale)** 으로 표시한다.
2. 하루 1회 배치(또는 stale 상태에서 첫 조회 시)로 요약을 새로 만들어 저장한다.
3. 프로필 화면은 **저장된 요약만 읽는다.** 화면을 열 때마다 AI를 호출하지 않는다.

이렇게 하면 비용이 후기 수에 비례할 뿐 조회 수와 무관하고, 응답도 즉시 뜬다.

### 2.2 저장 구조 (예정)

`profile_review_briefings`

| 컬럼 | 설명 |
|---|---|
| user_id | 대상 회원(기본키) |
| summary | 생성된 요약 문장 |
| review_count | 요약에 사용한 후기 수 |
| source_fingerprint | 사용한 후기 묶음의 해시(같으면 재생성 안 함) |
| provider, model | 어떤 AI로 만들었는지 |
| status | ok / stale / failed / hidden |
| generated_at | 생성 시각 |

- 읽기 권한: 로그인 회원이 공개 프로필을 볼 때만. 쓰기는 서버(Edge Function)만.
- 후기가 지워지거나 회원이 탈퇴하면 함께 지워진다.

### 2.3 입력·출력 규칙

- **입력:** 공개된 후기의 별점·코멘트·태그, 최대 20건(최신순). 작성자 이름과 식별 정보는 제외.
- **출력:** 한국어 2~3문장, 120자 내외. 사용한 후기 수를 함께 저장.
- **금지(요약 본문 생성 규칙, 그대로 유지):** 안전·신뢰 보증 표현("안전한 사람이에요"), 외모·성적 평가, 특정 후기 그대로 인용, 없는 사실 추가, 이름·장소 언급.
- **최소 조건:** 후기 N건 미만이면 카드를 **숨긴다**(N은 정책 결정 필요, 초안 3건).
- **실패 시:** 카드를 숨긴다. 오류 문구를 사용자에게 보이지 않는다.
- **항상 표시(D-A16, 2026-09-20 사용자 지정):** "사용자 리뷰를 바탕으로 동행 성향을 요약했습니다." — 표기 단어는 `특징 / 취향 / 성향` 중 **성향**을 추천(리뷰가 주로 시간 약속·대화 속도 등 동행할 때의 태도를 다루기 때문). 리뷰 건수를 함께 보이려면 "(리뷰 4건)"을 덧붙인다.
- ⚠️ 이전 문구 "공개된 후기 N건 기준 · 안전을 보증하는 정보는 아니에요"는 **사용자 지시로 삭제**했다. 안전 보증 오해를 막는 안내가 사라지므로, 안전 수칙 화면·공고 상세의 기존 안내로 보완할지 7-3에서 확인한다.

### 2.4 검수

- 사람이 확인하는 체크리스트: 후기에 없는 내용이 없는가, 보증하는 말투가 아닌가, 특정 후기를 그대로 베끼지 않았는가, 부정 후기를 숨겨 오해를 만들지 않는가.
- 부정 후기를 요약에 포함할지는 **D-A10 재확인 결과에 따른다.** 긍정만 요약하면 어떤 리뷰를 근거로 했는지 캡션에 밝힌다.

## 3. 기능 B — 공고 찾기 챗봇

### 3.1 접근 방식: AI는 "검색 조건"만 만든다 (권장)

```
사용자: "이번 주말에 성수에서 조용히 전시 볼 사람 있을까?"
   ▼ AI
{ "카테고리": ["전시"], "지역": "성동구·성수", "기간": "이번 주말",
  "키워드": ["조용한"], "정렬": "빠른 일정순" }
   ▼ 기존 공고 검색 (DB)
실제 공고 목록 → 기존 공고 카드로 표시
```

**왜 이 방식인가**
- AI가 공고를 지어낼 수 없다. 목록과 문구는 DB에서 그대로 온다.
- 기존 둘러보기 필터를 그대로 재사용한다.
- 값이 싸고 빠르다. 결과가 이상하면 어떤 조건으로 바뀌었는지 눈으로 확인·수정할 수 있다.

**화면**
- 이해한 조건을 **칩으로 보여주고 수정 가능**하게 한다: `전시 ×` `성수 ×` `이번 주말 ×`
- 그 아래에 평소 쓰는 공고 카드 목록.
- 0건이면 규칙 기반으로 완화안을 제안한다: "성수 → 성동구 전체로 넓혀볼까요?", "기간을 2주로 늘려볼까요?"
- 이해하지 못하면 되묻는다: "어느 지역에서 찾으시나요?"
- AI가 실패하면 **일반 필터 화면으로 조용히 되돌린다.**

**나중 단계(선택):** 공고 설명까지 의미로 찾는 벡터 검색. 공고 수가 충분히 쌓이고 조건 검색만으로 부족할 때 검토한다.

### 3.2 다룰 수 있는 조건

카테고리(12종), 지역, 기간(오늘·주말·N일 이내·특정 날짜), 키워드(제목·소개·태그), 작성자 성별·나이대, 연결 행사.

- 작성자 성별·나이는 **로그인 회원에게만** 적용하고, 화면에 "검색 편의를 위한 필터이며 신청 자격과는 별개예요"를 유지한다.
- **비공개 상세 주소는 검색 대상이 아니다.** 공개 지역만 쓴다.

### 3.3 안전·품질

- 검색어에 모욕·성적 요구·개인정보 요청이 들어오면 조건을 만들지 않고 안내로 끝낸다.
- 결과에 "AI가 이해한 조건" 표기를 항상 남겨 오해를 줄인다.
- 챗봇은 **공고를 대신 신청하거나 메시지를 보내지 않는다.** 찾아주기까지만 한다.

## 4. 공급자 전환 (포텐스닷 → 제미나이)

- Edge Function 안에 `callModel({system, input, schema, timeout})` 하나만 두고, 공급자별 어댑터를 그 뒤에 둔다.
- 전환은 환경변수 하나(`AI_PROVIDER=potens|gemini`)로 한다.
- 두 기능 모두 **JSON 형식 출력**을 요구하고, 형식이 깨지면 1회 재시도 후 실패 처리한다. (공급자마다 JSON 강제 방식이 다를 수 있어 어댑터에서 흡수)
- **확인 필요:** 포텐스닷의 엔드포인트·인증 방식·모델명·요청 형식·호출 한도·무료 범위·데이터 보관 정책. 사용자님이 문서나 키를 주시면 그에 맞춰 어댑터를 씁니다. 지금은 추정하지 않았습니다.

## 5. 단계별 진행

| 단계 | 내용 | 승인 필요 |
|---|---|---|
| P0 | **UI만 구현.** 브리핑 카드와 챗봇 화면을 더미 데이터로 만든다(D-A9 지시) | 없음(코드 작업) |
| P1 | Edge Function 골격 + 포텐스닷 어댑터. 테스트 데이터로만 호출 | 키 등록·배포 승인 |
| P2 | 브리핑 저장 테이블 migration, 배치 생성, 프로필 연결 | DB 적용 승인 |
| P3 | 챗봇 조건 변환 연결, 0건 완화 규칙, 한도·끄는 스위치 | 배포 승인 |
| P4 | 제미나이로 전환, 품질 비교 | 승인 |

**품질 점검:** 한국어 질의 20~30개(지역·기간·카테고리·모호한 표현·악용 시도)로 조건 변환 정확도를 측정하고, 브리핑은 10명 표본을 사람이 검수한다. 통과 기준은 사용자와 함께 정한다.

## 6. 결정이 필요한 것

1. **브리핑 최소 후기 수**(초안 3건)와 부정 후기 포함 여부 → D-A10과 함께.
2. **챗봇 위치:** 둘러보기 상단 검색창을 대체할지, 별도 버튼·탭으로 둘지.
3. **비로그인 사용 허용 여부**(허용하면 한도를 더 엄격히).
4. **AI 표기:** "AI가 요약했어요", "AI가 이해한 조건" 문구를 어떻게 쓸지.
5. **개인정보:** 후기 내용을 외부 AI에 보내는 것은 **처리위탁·국외이전 고지** 대상일 수 있다. 개인정보 처리방침과 가입 동의 문구 갱신이 필요한지 **법률 검토 필요**. 적법하다고 단정하지 않는다.
6. **비용 상한과 실패 정책:** 월 한도를 넘으면 기능을 끌지, 캐시만 제공할지.
7. **로그 보관:** 품질 점검을 위해 질의·요약 원문을 보관할지, 보관 기간.

---

## 7. 이 설계가 지키는 것

- AI가 공고나 후기를 **지어내지 못한다.** 목록·후기 원문은 언제나 DB에서 온다.
- AI가 죽어도 서비스는 **평소 필터와 프로필로 동작한다.**
- 개인 식별 정보는 외부로 나가지 않는다.
- 공급자 교체가 화면·DB에 영향을 주지 않는다.
