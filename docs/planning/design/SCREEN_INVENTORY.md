# 전체 화면 구조 초안 — 팀 합의용

작성: 2026-09-20. 사용자 확정 목적: **팀이 합의할 전체 화면 구조 만들기**.

상태: `초안 / 팀 합의 전`. 현재 GPT가 구조·흐름·상태를 설계하고 사용자·팀이 선택한다. 이 문서는 새로운 기능 도입, 실제 UI 구현, Figma 파일 생성 완료를 뜻하지 않는다.

## 설계 기준

- 기존 [Stitch 프롬프트](STITCH_PROMPTS.md)의 화면 ID를 유지한다. S01~S19에 S09-2·S09-3·S15-2를 포함해 **기존 22개 항목**이다. 화면 수가 19개라는 뜻이 아니다.
- S00 홈과 S20 자연어 검색을 구조 검토 항목으로 보완해 **주요 화면/흐름 24개**로 정리했다. 별도 페이지 24개를 구현한다는 결정이 아니다. 모달·탭 안의 영역·상태는 Figma에서 묶을 수 있다.
- S00 홈은 기존 디자인 기준으로 보존하고 진입 경로만 점검한다. S20은 D-A15의 검색 기능이지만 진입 위치와 화면 형태는 미정이다.
- 기존 프롬프트의 1·2·3차는 과거 UI 적용 순서다. 이번에는 전체 구조를 먼저 보고 한 흐름씩 시안을 만든다.
- [DESIGN.md](DESIGN.md)는 색·글꼴·컴포넌트 기준. [AI 설계](AI_FEATURES_DESIGN.md)는 초안과 D-A16 확정 문구를 구분한다.
- `골격 가능`: 배치·진입·종료 설계 가능. `부분 대기`: 해당 조건·문구만 미확정. `조건부`: 팀원 1의 범위 결정 뒤 추가. 미확정을 UI 생성 도구가 임의로 채우지 않는다.

## 정상 화면 외 공통 상태

각 주요 화면에는 해당하는 상태를 붙인다. 적용되지 않는 상태를 억지로 만들 필요는 없다.

- `default`: 기본 상태. `loading`: 불러오는 중. `empty`: 데이터/검색 결과 없음.
- `error`: 실패 원인과 재시도·돌아가기. `permission`: 비로그인/당사자 아님/제한 계정.
- `submitting`: 중복 제출 방지. `success`: 저장/신청 결과와 다음 행동.
- `expired`: 마감·기한 종료·삭제된 대상. `draft-exit`: 작성 중 이탈과 입력 보존.
- 신청 대기 → 확정 → 완료 → 평가 공개는 서로 다른 상태다. **채팅방 생성만으로 확정되지 않는다.**
- 공고 공개 지역과 확정 상대의 상세 장소를 같은 화면 데이터로 취급하지 않는다.

## Stitch → Figma 작업 방식

1. **전체 구조 합의:** 먼저 24개 주요 항목과 SX 후보에서 유지·통합·대기를 표시한다. 새 하단 탭이나 보조 기능을 생성 도구가 추가하지 않게 한다.
2. **현재 GPT의 입력 설계:** 화면 ID, 사용자 과업, 진입 조건, 필수 정보, 주요 버튼, 성공/실패/복귀, 정책 대기 부분을 한 장 설명으로 만든다.
3. **Stitch 시안:** [DESIGN.md](DESIGN.md)와 기존 해당 S 프롬프트에 이 설명을 함께 넣는다. 최신 D-A13~D-A16과 미결정 표시를 우선한다. 한 흐름을 작은 묶음으로 생성한다.
4. **Figma 구조 정리:** 실제 계정에서 가능한 내보내기/가져오기 경로를 확인한다. 직접 이동이 어려우면 시안을 참고해 편집 가능한 프레임으로 재구성한다. 이미지 한 장만 붙인 상태를 편집 가능한 와이어프레임 완료로 세지 않는다.
5. **검수 분담:** Gemini에는 빠진 상태·경로·시안 간 차이를 표로 찾게 한다. Claude에는 필요할 때 현재 코드/API와 다른 부분만 대조시킨다. 현재 GPT가 중요도와 수정안을 판단하고 사용자·팀이 선택한다.
6. **승인본:** Figma의 기준본은 하나로 관리하고 변경 이유·결정 ID를 붙인다. 서로 다른 AI의 화면안을 자동으로 합치지 않는다.

Figma 페이지 구성 제안: `00_전체구조`, `01_핵심동행`, `02_가입과작성`, `03_행사와프로필`, `04_정책대기`, `90_공통요소`.

프레임 이름 예시: `S02_공고상세_모집중_v01`, `S02_공고상세_마감_v01`. 화면 옆 주석에 `권한 / 진입 / 주요 행동 / 종료 / 관련 정책·API / 확정 여부`를 둔다. 첫 초안은 기존 모바일 기준을 활용하고 세부 픽셀·애니메이션보다 계층과 흐름을 우선한다.

## 함께 시작할 첫 묶음

전체 목록을 한 번 검토한 뒤 **S01 둘러보기 → S02 공고 상세 → S08 신청 → S10 채팅 목록 → S11 대화·작성자 최종 수락 → S16 약속 상세**의 연결부터 그리는 것을 추천한다. S14 상대 프로필은 판단을 돕는 분기로 붙인다. 새 계정의 인증은 S05~S07 분기로 표시한다.

이유: 서비스의 중심인 ‘상대를 판단하고 신청한 뒤 대화하고 확정하는 구조’를 팀이 같은 의미로 이해해야 나머지 화면을 배치할 수 있다. 완료·평가 S17, 작성자 공고 등록 S03/S04를 다음 연결로 붙인다. 6개 화면만 만들고 전체 목록을 생략한다는 뜻이 아니다.

첫 구조 검토의 질문은 두 가지다: 신청 후 대화와 최종 확정이 구분되는가? 각 역할이 다음 행동과 되돌아갈 곳을 알 수 있는가? 이는 팀 검토 기준이며 실제 사용자 검증 결과가 아니다.
