# 유미당 추가 요구 사항 — 확정 내용과 결정 이유

- 갱신일: 2026-09-22
- 기준: 팀 회의 최신안 [PRD.md](./PRD.md)와 이번 대화에서 사용자가 확정한 사항.
- 반영 대상: [yumidang-wireframes.html](../design/yumidang-wireframes.html). PRD 원문은 유지한다.
- 현재 상태: 확정 내용을 와이어프레임에 반영하고 로컬 브라우저 점검 완료. 실제 API 연동은 아직 수행하지 않았다.
- 이유 표기: 사용자가 직접 밝힌 이유는 ‘사용자 이유’로, 선택한 안의 취지를 설명한 것은 ‘설계 근거’로 적는다. 설계 근거를 사용자 발언이나 검증된 효과로 취급하지 않는다.
- 이 문서에는 채택한 내용만 남긴다. 이전의 미채택 대안·추가 제안·API 조사 전문은 정리했다.

## 1. 회원가입 — 여성 전용과 프로필 입력

### 1-1. 로그인·가입(S05~S07): 성인 여성만 이용

- 확정: 성인 여성만 가입·이용한다. 휴대폰 본인인증으로 이용 자격을 확인하며, 직접 입력한 성별·생년월일로 이를 대신하지 않는다(PRD 기준).
- 제거: 남성 가입 분기, 추천 코드에 의한 예외 가입, 학교·직장 이메일에 의한 예외 가입, ‘나’의 추천 코드 발급·복사. 둘러보기·공고 작성의 남성/여성/성별 무관 선택도 제거한다.
- 이유: 사용자가 “오로지 여성 유저만 이용 가능”이라고 확정했고, 최신 PRD와 동일한 가입·이용 자격을 화면 전체에 적용하기 위해서다.

### 1-2. 가입 프로필(S06): 사진만 필수, 나머지 선택

- 확정: 프로필 사진은 필수. 취향·대화 방식·MBTI는 모두 선택이며, 입력하지 않아도 가입을 완료할 수 있다.
- 정정: 앞서 기록한 ‘취향·대화 방식 각각 1개 이상 필수’는 사용자의 최신 지시로 폐기한다.
- 사용자 이유: 필수 범위를 사진으로 한정하라고 명시했다. 별도의 동기는 밝히지 않았다.
- 설계 근거: 취향 정보를 아직 정하지 않은 사용자도 사진 등록 후 가입할 수 있게 한다.

### 1-3. 가입 프로필(S06)·프로필 편집(S15-2): 버튼과 직접 입력

- 확정: 사진을 등록하는 가입 흐름에서 취향·대화 방식·MBTI를 함께 입력할 수 있게 한다. 가입 후 편집에도 같은 입력 방식을 사용한다.
- 취향: 동행 카테고리 버튼과 직접 입력해 추가하는 기능을 제공한다.
- 대화 방식: 활발함·차분함·에너지 넘침 등 다양한 버튼과 직접 추가 기능을 제공한다.
- MBTI: 작성칸을 누르면 화면 중앙에 4열×2행 패널을 연다. 윗줄 E/S/T/J, 아랫줄 I/N/F/P, 두 줄 사이 가로 구분선. 각 열에서 하나씩 골라 네 글자를 작성칸에 표시한다.
- 설계 근거: 기본 선택지로 빠르게 입력하면서 정해진 항목에 없는 취향도 표현하게 하고, MBTI를 네 쌍의 선택으로 입력하게 한다.

## 2. 공고·프로필·채팅 — 이름 공개와 선택 인증

### 2-1. 공고 목록·상세(S01/S02), 프로필(S14), 채팅·약속(S11/S16): 상대에 따른 이름 공개

- 확정: 비로그인은 ‘동행 123’ 형태의 시스템 별칭, 로그인한 일반 회원은 ‘김*연’처럼 마스킹한 이름, 확정된 동행 상대에게는 전체 실명을 표시한다.
- 적용: 같은 사람의 프로필이라도 보는 사람과의 확정 관계에 따라 표시가 달라진다. 확정 당사자의 실명을 제3자에게 공개하지 않는다.
- 설계 근거: 공개 탐색 단계의 신원 노출을 줄이고, 실제 만남이 확정된 상대끼리는 이름을 확인할 수 있게 한다.
- 결정 출처: 사용자가 이름 마스킹 안에 ‘확정 상대에게 전체 실명, 비로그인에게 시스템 별칭’을 직접 추가했다.

### 2-2. 나(S13) → 안전·계정 → 인증 관리: 학교·직장 이메일 확인

- 확정: 가입 후 ‘나 → 인증 관리’에서 선택적으로 진행한다. 가입 자격을 대신하는 수단으로 사용하지 않는다. 최신 화면 수정 요청에 따라 별도 가입 완료 화면과 그 화면의 선택 인증 진입은 없애고, 완료 안내 팝업 후 홈으로 이동한다.
- 표시: 인증 완료 배지는 명칭 대신 아이콘으로 표시한다. 인증한 이메일 주소와 도메인은 다른 회원에게 공개하지 않는다.
- 설계 근거: 가입 과정에 선택 인증을 필수처럼 끼워 넣지 않고, 사용자가 인증 상태를 한곳에서 관리하게 한다. 이메일 확인을 현재 재학·재직 상태의 보증으로 표현하지 않는다.
- 결정 출처: 1B 선택 후 사용자가 배지를 아이콘 방식으로 지정했다.

## 3. 공고 등록·신청·채팅 — 유료 동행과 양쪽 최종 동의

### 3-1. 공고 작성(S03/S04)·목록/상세(S01/S02): 유료 요청형과 제공형

- 확정: 무료/유료 동행을 구분하며 유료는 요청형과 제공형을 모두 지원한다.
- 요청형: 작성자가 동행을 구하고 상대에게 비용을 지급한다.
- 제공형: 작성자가 동행을 제공하고 상대에게 비용을 받는다.
- 표시: 공고와 신청·확정 과정에서 금액과 지급 방향을 구분한다. 유료 동행과 계좌 인증은 SX07의 제외 목록에서 실제 설계 범위로 옮긴다.
- 설계 근거: 도움을 구하는 수요와 동행을 제공하는 수요를 모두 담고, 누가 돈을 내는지 혼동하지 않게 한다.
- 결정 출처: 2C 선택 및 유료 기능의 실제 범위 이동 승인.

### 3-2. 유료 공고 등록(S03/S04)·신청(S08): 1원 계좌 인증 필수

- 확정: 유료 공고 등록자와 신청자 모두 1원 계좌 인증을 완료해야 하며, 인증된 사용자끼리만 유료 매칭할 수 있다. 무료 동행까지 계좌 인증을 필수로 확대하지 않는다.
- 설계 근거: 유료 거래에 참여하는 양쪽에 같은 계좌 인증 조건을 적용한다.
- 범위: 계좌 인증은 동행 대금 결제·정산 완료와 구분한다. 결제·정산·수수료·환불·취소 보상의 세부 정책은 이번 결정에 포함하지 않는다.

### 3-3. 채팅 탭(S11), 공고 상세의 상대 선택(S02), 나의 받은 신청(S13): 양쪽 최종 동의 후 확정

- 확정: 신청 → 대화 → 작성자가 상대 선택 → 신청자가 최종 조건에 동의 → 동행 확정. 무료·유료에 같은 방식을 적용한다.
- 변경: 작성자가 신청을 수락하거나 상대를 선택한 것만으로 바로 확정하지 않는다. 어느 화면에서 상대를 선택해도 같은 최종 동의 단계로 연결한다.
- 확인 내용: 일정, 공개된 만남 지역, 유료인 경우 금액과 지급 방향. 정확한 만남 주소와 상대 실명 공개는 최종 확정에 연결한다.
- 사용자 이유: 신청자는 여러 공고를 비교·대화 중일 수 있는데, 작성자 수락만으로 원치 않는 약속이 확정될 수 있다는 설명을 이유로 이 방식을 선택했다.
- 설계 근거: 신청한 시점과 대화 이후의 판단이 달라질 수 있으므로, 실제로 그 상대와 만나겠다는 의사를 마지막에 확인한다.
- 함께 감수하는 점: 신청자의 최종 응답을 기다리는 단계가 하나 늘어난다.

## 4. 홈·둘러보기 — AI 대화와 주변 공고 검색

### 4-1. 홈(S00)·U/둘러보기(S01) → AI 대화(S20)

- 확정: 기존 ‘+’ 버튼 바로 위에 ‘AI’ 버튼을 둔다. 누르면 전체화면 대화로 진입한다. 새 하단 탭은 추가하지 않는다.
- 입력: 취향·지역·성향·대화 방식·원하는 상대 MBTI 등을 자연어로 말하고 대화하며 조건을 다듬는다.
- 결과: 해석한 조건을 수정 가능한 칩으로 표시하고, 등록된 공고와 추천 이유·확인할 점을 제시한다. 현재 대화의 명시적 조건을 프로필보다 우선하며, 상대 MBTI 미입력만으로 자동 탈락시키지 않는다.
- 이용: 비로그인 기존 회원은 로그인 후 AI로 복귀한다. 신규 가입을 진행한 경우에는 최신 화면 수정 요청에 따라 가입 완료 안내 팝업 후 홈으로 이동한다. 대화의 장기 자동 저장은 기본으로 제공하지 않는다.
- 설계 근거: 사용자가 필터를 하나씩 조작하지 않아도 원하는 동행을 설명하고, AI의 조건 해석을 직접 확인·수정하게 한다.
- 결정 출처: 사용자의 AI 버튼 위치 지정과 3A 선택.

### 4-2. U/둘러보기(S01)·AI(S20): 장소 선택 후 주변 공고를 목록으로 탐색

- 확정: 장소를 선택해 주변 공고 목록을 제공한다. 둘러보기와 AI에서 같은 장소·검색 범위 조건을 사용한다(L-A).
- 역할: Kakao로 기준 장소를 찾고, 그 기준과 취향 조건에 맞는 유미당 공고를 검색한다. 같은 이름의 장소가 여러 개면 주소를 붙인 후보로 구분한다.
- 설계 근거: 일반 검색과 AI 대화에서 같은 기준으로 공고를 찾고 비교하게 한다.

### 4-3. 주변 공고 검색·정렬·거리 표시(S01/S20): 공개 동네의 대표 위치 사용

- 확정: 확정 전 공고 검색과 거리 정렬은 공개된 동네의 대표 위치를 기준으로 한다. ‘공개 지역 기준 대략적인 거리’라고 안내한다. 비공개 만남 좌표를 검색·정렬의 기준으로 사용하지 않는다.
- 설계 근거: 정확한 거리 표시나 반복적인 반경 검색으로 비공개 만남 지점을 좁히는 것을 줄이면서 주변 탐색을 제공한다.
- 함께 감수하는 점: 표시한 거리는 실제 만남 지점까지의 정확한 거리가 아니다.
- 결정 출처: 사용자가 L-A를 선택하면서 이 위치 기준을 명시적으로 승인했다.

## 5. 공고 작성·행사 탐색 — 장소 API와 행사 데이터 연결

### 5-1. 공고 작성(S03)의 장소 입력: 장소명 검색 + 주소 검색

- 확정: 장소명 검색을 기본으로 제공하고 ‘주소로 찾기’를 함께 제공한다(A-B). 후보 선택 후 주소를 자동 입력하고 ‘3번 출구 앞’ 같은 상세 만남 지점을 작성한다.
- 적용: 장소명은 Kakao Local, 도로명·지번·우편번호 선택은 우편번호 서비스를 연결한다. 공개 미리보기는 시·구·동, 정확한 주소와 상세 만남 지점은 확정 상대에게 표시한다.
- 설계 근거: 카페·공연장 이름만 아는 경우와 정확한 주소를 아는 경우 모두 같은 공고 작성 흐름에서 입력하게 한다.

### 5-2. 홈 행사(S00)·행사 목록(S09-2)·행사 상세(S09-3): 공연·전시·축제 통합 탐색

- 확정: 기존 행사 목록에 공통 카드로 통합하고 지역·기간·유형으로 탐색한다(E-A). 상세에서 출처를 표시한다.
- 데이터 연결: 공연은 KOPIS, 서울 전시·축제는 서울 열린데이터광장, 전국 축제는 TourAPI를 사용한다.
- 연결: 행사 상세에서 관련 동행 공고를 보거나 해당 행사로 공고를 작성한다. 행사장을 장소 후보로 채우되 실제 동행 날짜·시간·만남 지점은 작성자가 확인한다.
- AI: 행사 카드와 동행 공고 카드를 구분한다. 행사는 있지만 공고가 없으면 해당 행사로 모집하는 경로를 제공한다.
- 표시: 행사 입장료와 동행 비용은 구분한다. 공연·행사 기간만으로 특정 날짜의 회차·휴관 여부·잔여석이 확인됐다고 표시하지 않는다.
- 설계 근거: 사용자가 데이터 제공기관을 몰라도 하나의 흐름에서 행사를 찾고 동행으로 연결하게 한다.

### 5-3. 홈(S00)·행사 목록(S09-2): 새 행사 기본 노출 + 진행 중 포함 선택

- 확정(A안): 홈은 ‘이번 주 새로 시작한 행사’를 중심으로 보여준다. 행사 목록도 이를 기본으로 하되, ‘진행 중인 행사도 포함’을 켜면 선택한 기간과 행사 기간이 겹치는 장기 행사까지 포함한다.
- 사용자 이유: 행사가 너무 많이 쌓이는 것을 막기 위해 기존에 ‘그 주에 시작한 행사만’ 기준을 사용했다고 밝혔다. 설명 후 A안을 승인했다.
- 설계 근거: 처음에는 새 행사를 간결하게 보여주고, 더 찾아보고 싶을 때는 오래 진행하는 전시도 찾을 수 있게 한다. 토글은 행사 기간의 포함 범위를 바꾸며, 노출 개수 제한이나 추천 순위를 새로 확정한 것은 아니다.

### 5-4. AI(S20)의 ‘이번 주말 갈 전시 찾아줘’: 장기 전시와 신규 전시 함께 검색

- 확정: 주말과 행사 기간이 겹치는 장기 전시를 검색하고, 이번 주 새로 시작한 전시도 그 주말과 기간이 겹치면 함께 포함한다. 신규 전시에는 ‘이번 주 새로 시작’ 표시를 붙인다.
- 제외 예시: 이번 주 월요일에 시작했어도 금요일에 끝나는 전시는 주말 검색에서 제외한다. 지난달 시작했더라도 이번 주말까지 이어지는 전시는 포함한다.
- 구분: 홈·행사 목록의 ‘새로 시작’ 기본값을 AI의 주말 검색에 그대로 적용하지 않는다. 사용자가 명시적으로 ‘이번 주 새로 시작한 전시’만 요청하면 그 조건으로 좁힌다.
- 결정 출처: 사용자가 A안을 승인하면서 AI 주말 검색에 신규 전시도 포함하되 주말 진행 조건을 만족해야 한다고 직접 추가했다.
- 설계 근거: ‘새로운 행사 발견’과 ‘내가 갈 수 있는 기간의 행사 찾기’는 다른 탐색 목적이므로 화면과 요청의 목적에 맞춰 포함 범위를 정한다.

### 5-5. 행사 카드·상세(S09-2/S09-3)·AI(S20): 기간과 실제 운영 여부 구분

- 확정: 행사 기간에 포함된다는 것만으로 그날 실제 운영한다고 안내하지 않는다. 휴관일·공연 회차는 제공된 운영 안내·공식 페이지에서 확인하도록 한다.
- 설계 근거: 장기 전시에는 휴관일이 있고 공연은 날짜별 회차가 다를 수 있으므로, 시작일·종료일만으로 방문 가능 여부나 잔여석을 보장할 수 없다.
- 결정 출처: 사용자가 해당 안내를 명시적으로 승인했다.

## 6. 완료 동행·공개 프로필 — 상호 평가와 받은 리뷰

### 6-1. 나의 완료 동행(S13)·약속 상세(S16) → 평가(S17): 두 단계 평가

- 확정: 한 바텀시트에서 ‘좋아요 / 보통이에요 / 별로예요’를 먼저 선택한다.
- 좋아요: 별점 1~5 + 칭찬 키워드(선택, 최대 3개) + 한마디(선택).
- 보통이에요/별로예요: 별점 1~5 + 한마디(선택).
- 칭찬 예시: 시간을 잘 지켜요, 연락이 잘돼요, 웃음이 많아요, 대화가 잘 통해요.
- 설계 근거: 전체적인 동행 경험을 먼저 선택하고, 좋았던 경험에는 구체적인 칭찬을 간단히 추가하게 한다.
- 결정 출처: 사용자의 최초 평가 요구와 4A 선택.

### 6-2. 평가 작성 중(S17): 제출 전 뒤로가기, 제출 후 수정 불가

- 확정: 별점·한마디 단계에서 감정 선택 단계로 돌아가 선택을 바꿀 수 있다. 최종 제출 성공 후에는 수정할 수 없다.
- 설계 근거: 제출 전에는 판단을 고칠 수 있게 하고, 제출된 평가의 내용은 고정한다.
- 결정 출처: 사용자가 4A 선택 시 뒤로가기와 수정 불가 시점을 직접 명시했다.

### 6-3. 공개 프로필(S14)·나의 받은 후기(S13): 차트 → AI 요약 → 원문 리뷰

- 확정: 칭찬 키워드 가로 막대 차트, AI 리뷰 요약, 사용자 리뷰 순서로 배치한다(5A).
- 차트: 좋아요 평가에서 받은 칭찬의 누적 횟수를 표시한다. 상위 5개를 보여주고 가장 많은 키워드를 기준으로 막대 길이를 비교한다.
- AI 요약: 공개 리뷰 3개 이상부터 제공하며 기준 리뷰 수를 표시한다. 비공개 처리된 리뷰는 제외하고 요약이 실패해도 원문 리뷰는 볼 수 있게 한다.
- 설계 근거: 자주 받은 칭찬을 먼저 훑고 요약을 읽은 뒤, 실제 리뷰 내용으로 판단을 확인하게 한다.
- 수치의 성격: 선택한 안의 최대 3개 칭찬·상위 5개 표시·리뷰 3개 기준은 초기 설계값이며, 사용자 효과가 검증된 수치는 아니다.

### 7-4. S01 검색과 필터 후속 수정 (2026-09-22)

- 사용자 확정: 둘러보기 검색은 공고 제목 또는 공고의 만남 장소를 대상으로 한다. 입력 안내를 ‘공고 제목 또는 만남 장소’로 바꾸고 검색 버튼·Enter 실행, 공백 정리를 반영했다.
- 기존 공개 범위 유지: 만남 장소 검색은 공개된 지역을 대상으로 하며, 비공개 상세 주소·만남 지점은 결과 판정에도 사용하지 않는다. 설계 근거: 검색 일치 여부로 비공개 지점을 알아내는 것을 막는다.
- 사용자 확정: S01 필터의 선택 장소/반경 표시, 1·5·10 km 칩, 대략적인 거리 안내를 제거한다. 이전 ‘선택 장소 없음 유지’ 의견보다 이번 지시를 우선한다.
- 범위: 동행 비용 필터, 별도 장소 주변 찾기, AI의 반경 조건은 유지했다.
- 로컬 확인: 구문·검색/필터 검증 17개 및 브라우저에서 제목/공개 지역 검색, Enter 실행, 빈 검색 복원, 비공개 주소 검색 제외, 지정 요소 제거와 기존 동행 비용·AI 반경 유지 확인. 실제 API·서버 검색은 미연동이다.
