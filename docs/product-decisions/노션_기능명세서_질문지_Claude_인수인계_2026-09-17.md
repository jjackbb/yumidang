## 1. 사용자: 이 파일 사용 방법

1. 아래 **52개 질문**을 읽고 답안표에 A/B 또는 직접 의견을 적는다. 추천은 자동 선택되지 않는다.
2. 한 번에 결정하기 어려운 질문은 `보류: 이유`로 적는다. 제재 수치·보존기간은 근거 없이 정할 필요 없다.
3. 이 파일 경로와 답안표를 Claude Code에 전달한다. 아래 복사용 요청문을 사용하면 된다.
4. Claude는 이미 확정한 결정을 다시 묻지 않고, 답변한 항목을 관련 기능 전반에 반영한다. 선택끼리 충돌하거나 꼭 필요한 값이 비면 해당 항목만 추가 질문한다.

추천 근거는 제품 설계 판단이다. 사용자 실험 결과나 법률 검토 결과가 아니다. 새로운 숫자는 명시적으로 선택하더라도 **검증 전 정책 가설**로 기록한다.

## 5. 기존 명세의 유지 기준

아래는 현재 노션에 있는 기준이다. 이번 대화에서 모두 재승인한 것은 아니며 변경하려면 해당 질문에 사용자 선택이 필요하다.

- 공고당 활성 동행 1명, 작성자 수락 시 즉시 매칭. 요청 수락·Match 생성·공고 마감·다른 신청 처리의 일관성 보장.
- 재신청은 이전 신청과 이력을 남기고 새 request_id 생성. 작성자가 거절한 같은 공고에는 재신청 불가.
- 완료 동행 취소 금지. 차단 시 진행 중 동행 취소, 완료·신고 기록 보존.
- 관심친구는 단방향 비공개 저장. 초대는 신청도 매칭도 아님. 공개 공고 → 초대 → 수신자 직접 신청 → 작성자 수락.
- 관심친구의 새 공고 알림 기본 켜짐·사람별 끄기. 처음 보는 사람은 수신자가 저장하지 않았고 실제 동행 경험도 없는 발신자. 알림을 꺼도 초대 기록 유지.
- 받은 초대 최신순에서만 관심친구 묶음 우선. 시간순은 묶음 없이 전체 동행 시작이 빠른 순. 과거 동행만으로 상단 고정하지 않음.
- 완료된 동행당 각 1회 평가. 후기 선택, 블라인드 공개는 양측 제출 또는 평가기간 종료. 기본 평가기간 7일.
- 당도 초기 15·최대 100·정수·완료 횟수 가점 없음. 기존 산식의 별점/후기 중복과 최저값은 Q15·18에서 결정.
- 전화는 P1, 유료 동행은 무료 MVP와 별도. 기능을 임의로 삭제하지 않기.

## 6. 전체 질문

모든 질문에 A/B 외 **직접안** 또는 **보류**로 답할 수 있다. 직접안은 필요한 값과 예외를 함께 적으면 좋다. “A가 추천”이라고 자동 가정하지 말 것: Q15는 B 추천이며 Q27도 B 추천이다.

### 공고·신청·일정 변경

#### Q01. 공고 수동 마감 후 기존 신청

관련 기능: POST-03, POST-04, MATCH-03~05, CHAT-01·03, FAVORITE-02

- **A:** 신규 신청만 막고 기존 신청은 원래 모집 마감 시각까지 수락 가능. 기존 신청자 채팅도 그때까지 유지.
- **B:** 기존 대기 신청도 즉시 종료하고 새 메시지·수락 제한.
- **판단 근거·추천:** A: 후보가 충분할 때 모집만 멈추고 고를 수 있음. 수동 모집중단과 시각 만료 상태를 구분해야 함.

#### Q02. 공고 취소와 확정 동행 취소 구분

관련 기능: POST-03, MATCH-09, CHAT-01·03·04, NOTI-01

- **A:** 공고 취소 시 대기 신청 전부 종료, 채팅 기록 보존·새 메시지 제한. 이미 확정된 동행은 별도의 동행 취소 절차 사용.
- **B:** 공고 취소 확인 화면에서 확정 동행 취소까지 함께 실행하되 영향·사유를 명시.
- **판단 근거·추천:** A: 단순 공고 관리로 약속이 취소되는 실수를 줄임. 직전 대화의 두 질문은 아직 답을 받지 않았음.

#### Q03. 공고 조건 변경의 재확인 범위

관련 기능: POST-02, MATCH-06, MATCH-04

- **A:** 일정·지역/장소·상대 조건·활동 내용 등 신청 판단에 영향을 주는 변경은 재확인, 의미 없는 오탈자만 제외.
- **B:** 내용을 조금이라도 수정하면 모든 대기 신청자에게 재확인.
- **판단 근거·추천:** A: 불필요한 확인을 줄이지만 의미 있는 변경의 판정 기준이 필요. 애매하면 재확인 처리.

#### Q04. 변경 조건에 응답하지 않거나 거절한 신청

관련 기능: MATCH-06, POST-04, CHAT-03

- **A:** 미응답은 수락 보류 후 모집 마감 시 만료, 거절은 해당 신청 종료(작성자 거절과 구분하여 재신청 가능).
- **B:** 동의하지 않은 기존 신청은 즉시 종료하고 새 조건으로 다시 신청하도록 함.
- **판단 근거·추천:** A: 사용자의 응답 시간을 보장. 기존 약속이 없는 대기 신청에만 적용.

#### Q05. 매칭 전 상세 장소 변경 안내

관련 기능: POST-02, MATCH-06, DISC-03

- **A:** 지역 변경과 '상세 장소 변경됨' 사실만 안내하고 정확한 주소는 계속 숨김. 확정 후 공개.
- **B:** 매칭 전 상세 장소 수정은 금지하고 공고 취소 후 새로 작성.
- **판단 근거·추천:** A: 확정 전 주소 비공개라는 기존 결정 유지. 숨겨진 주소 자체에 동의했다고 기록하면 안 됨.

#### Q06. 동시에 여러 일정·장소 변경 제안

관련 기능: MATCH-08, NOTI-01

- **A:** 매칭당 대기 제안 1건만 허용. 해결하거나 제안자가 철회한 뒤 새 제안 가능.
- **B:** 새 제안이 이전 제안을 대체. 이전 제안은 대체됨 표시하고 상대에게 알림.
- **판단 근거·추천:** A: 서로 다른 제안에 동의하는 혼선을 줄임.

#### Q07. 일정 변경 제안의 응답 기한

- **B:** 완료 통지 후 48시간으로 확대하고 나머지는 A와 동일.
- **판단 근거·추천:** A: 문서의 기존 24시간을 유지하되 미접속자가 놓칠 수 있음. 시간은 운영 가설이며 접근 가능성과 함께 검증.

- **판단 근거·추천:** A: 시작 전 불발도 기록하되 아직 오지 않을 시점에 노쇼라고 판정하지 않음.

#### Q14. 분쟁 판정 후 완료·평가 처리

#### Q15. 평가 입력 구성과 점수 중복

- **B:** 별점과 자유 후기는 유지하되 당도는 별점만 반영. 후기 반응·칭찬은 근거 정보로만 표시.

관련 기능: SUSP-09, ADMIN-01·02, SUSP-08

- **A:** 일반 검토자와 조치 권한자를 구분. 근거 열람은 필요한 역할에 제한·접근 기록 보존. 기존 이력은 덮어쓰지 않고 정정 이력 추가. 증빙 파일 기술 제한은 안전한 초안 작성 후 사용자 확인.
- **B:** 초기 운영자는 한 역할로 두되 사유·처리자·접근 기록·정정 이력은 모두 유지.
- **판단 근거·추천:** A: 권한과 감사 흔적을 분리. 실제 인력이 한 명이면 B가 현실적일 수 있음.

#### Q51. 불발·분쟁 상태 표현

관련 기능: NOSHOW-01, COMPLETE-02, ADMIN-02, TRUST-03

- **A:** 신고 사건의 접수/검토/판정 상태와 동행 상태를 분리. 동행은 분쟁 중 여부로 완료·평가 반영 보류, 노쇼는 운영 판정 결과로 기록.
- **B:** 노쇼검토·완료이의검토 등을 동행의 별도 상태로 모두 표현(전이표 추가).
- **판단 근거·추천:** A: 신고가 접수됐다는 사실을 노쇼 확정으로 오해하지 않음. 세부 영문 코드는 Claude가 문서 내부에서 일관되게 정리하고 실제 DB 스키마라고 주장하지 않음.

#### Q52. 평가 제출 후 수정

관련 기능: REVIEW-01·02·03, TRUST-01

- **A:** 제출 전 미리보기·확인 제공, 제출 후 직접 수정 불가. 잘못된 내용은 신고/지원 경로로 정정 판단.
- **B:** 공개 전이면서 평가기간 내에는 수정 가능, 공개 후 수정 불가.
- **판단 근거·추천:** A: 상대 평가 공개 후 수정으로 보복하는 경로를 단순하게 막음. B는 오입력 수정에 유리하나 공개 시점의 동시처리 필요.

## 8. Claude 작업 절차

1. 답안표를 질문 ID와 연결하고 ‘선택 / 직접안 / 보류 / 미응답’을 구분한다. 이 문서의 추천 이유를 사용자의 선택 이유로 꾸며 쓰지 않는다.
2. Notion 연결과 복제 페이지 읽기·쓰기 가능 여부를 확인한다. 도구를 사용할 수 없다면 연동이 있다고 가정하거나 완료를 주장하지 않는다.
3. 최신 복제 페이지를 조회하고 로컬 스냅샷과 차이를 본다. 사용자 이후 수정은 보존한다. 기술 도구명·스키마는 실제 제공된 정의를 따른다.
4. 답변에 따라 **변경 행과 새 내용이 보이는 로컬 수정안**을 먼저 만든다. 이번 사용자가 선택한 정책을 노션에 반영하는 것은 인수인계 요청 범위에 포함된다. 별도 전체 승인 요청을 반복하지 않는다.
5. 정책 충돌·누락값만 1~3개씩 묶어 물으면서 독립적으로 확정 가능한 항목은 진행한다. 무응답은 승인 아님.
6. 표의 기존 열·행·순서·색·이미지·자식 문서를 보존하고 필요한 행/문구만 수정한다. 입력/출력만 수정하고 같은 행 정책을 충돌 상태로 남기지 않는다.
7. 표준 용어: 회원 user_id / 공고 post_id / 신청 request_id / 확정 동행 match_id / 채팅 chat_id / 평가 review_id / 초대 invitation_id / 신고·분쟁 case_id / 제재 sanction_id. 실제 DB 마이그레이션은 하지 않는다.
8. 논의가 끝난 문구는 ‘확정 정책’으로 이동/정리한다. 단순히 “확인 필요” 단어를 삭제하여 해결된 것처럼 만들지 않는다. 보류는 이유·담당·다음 근거·출시 영향이 있는 별도 목록으로 남긴다.
9. 표 위에 핵심 결정 요약, 표 아래에 변경 이력과 잔여 항목을 간결하게 기록한다. 사용자 동의가 없는 추천은 본문 확정 정책으로 넣지 않는다.
10. 저장 후 다시 조회하고 항목별 대조 결과를 남긴다. 읽기 결과가 잘렸거나 알 수 없는 블록이 있으면 누락 없이 읽은 것처럼 판단하지 않는다.
11. 마지막 보고는 ‘반영한 질문 / 보류·미응답 / 남은 충돌 / 확인 결과’로 한다. 원본 페이지·코드·DB·배포는 변경하지 않는다.

### 선택 간 연결에서 꼭 확인할 것

- Q01 A이면 수동 모집중단과 모집기한 만료를 구분. DISC-03의 일반 ‘마감 시 버튼 비활성’, CHAT 종료, FAVORITE 신규 초대도 함께 맞춘다. 수동 마감 뒤 기존 신청 수락은 가능하지만 새 초대·새 신청은 불가.

- Q11 자동완료는 예상 종료와 실제 완료를 구분. 분쟁 건 자동완료 금지. Q12·14·17과 평가 기한/공개/집계 보류를 함께 맞춘다.

- Q18은 한도 밖 원점수 보존 여부까지 선택. 재계산 시 무효 평가·잘못된 제재를 원인 단위로 되돌린다.
- Q19는 점수 변화로 블라인드 평가가 새지 않도록 공개 가능 시점과 연결. 제재 점수는 평가 공개 규칙과 별도 원인으로 처리.

- Q28 A여도 이미 문서에 있는 영구 정지 설명은 초기 도입 완료가 아닌 후속 범위로 정리. 정지 중 로그인·조회 허용 결정은 유지.
- Q30 A와 Q31 A의 조합은 이미 시작한 동행을 검토할 실제 대응 인력 공백이 있을 수 있다. 운영검토 화면 존재만으로 대응 가능하다고 하지 않는다.

- Q36은 개인정보/증빙의 구체 보존기간 법적 적합성을 확정하지 않는다. 최신 권위자료 검토가 필요한 업무는 따로 남긴다. 기존 30일/5년은 근거 검토 전 법정 의무로 표현하지 않는다.
- Q37~38은 탈퇴 즉시 공개 정보 비노출과 필요한 자료의 제한 보관을 구분. 활성 제재 우회 방지 목적으로 무제한 신원 보관을 추가하지 않는다.
- Q39~45에서 알림 끄기·초대 종료·저장 해제를 신청/매칭 취소와 혼동하지 않는다.

- Q48 문자 인증 성공은 실명/성인 인증을 입증하지 않음. KYC 및 실제 SMS 구현 여부는 이 명세 작업에서 검증하지 않았음.
