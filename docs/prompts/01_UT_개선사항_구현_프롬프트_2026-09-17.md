### 3. 구현 범위

각 항목은 `현재 동작 감사 → 결함 재현 또는 이미 해결된 증거 → 최소 수정 → 회귀 테스트` 순서로 처리하세요.

#### A. P0: 핵심 흐름과 신뢰를 깨는 문제

1. 화면에 남은 하드코딩 더미 이름·전화번호·테스트 개인정보를 제거하세요. 실제 DB 데이터를 삭제하라는 뜻은 아닙니다.
2. 실제로 구현되지 않은 `긴급 SOS 버튼` 안내가 있으면 제거하세요. 신고·차단 등 실제 제공 기능만 설명하세요.
3. 가입·로그인 진입 화면의 제목과 주요 버튼을 명확히 하고, 이미 가입된 번호가 가입 흐름으로 들어오면 이해 가능한 안내 뒤 로그인으로 연결하세요. 현재 Auth 보안 계약은 유지하세요.
4. 참여 신청 알림이 생성·표시·읽음 상태까지 이어지는지 확인하고, 누락이 재현되면 수정하세요.
5. 공고 시작·종료 입력에서 종료가 시작보다 빠르거나 같으면 프론트와 서버 모두 거부하세요. 과거 날짜 제한은 기존 확정 계약이 있을 때만 적용하세요.
6. 공고 등록 성공 뒤 사용자가 방금 작성한 글을 찾을 수 있도록 해당 공고 상세 또는 `나의 공고`로 이동하고 성공 상태를 보여주세요.
7. 양쪽 모두 평가했는데 `상대 평가 대기 중`으로 남는 결함을 재현하고 수정하세요. D10~D12의 24시간 이의기간·7일 평가기간·분쟁 동결 계약은 유지하세요.
8. ISO 원문 시각이 카드에 그대로 보이지 않도록 사용자 지역 기준 형식으로 표시하세요. 저장 값은 변경하지 마세요.
9. 상세 화면에는 키보드·브라우저 뒤로가기를 포함한 명확한 복귀 경로를 제공하세요.

#### B. P1: 참여 판단을 돕는 정보 구조

1. 공고 목록·상세·채팅 헤더에서 필요한 범위의 `성별·만 나이/연령대·날짜·시간·공개 지역`이 일관되게 보이는지 감사하고 누락만 보완하세요. 생년월일과 정확한 장소는 노출하지 마세요.
2. 성별·연령대 필터를 추가하되 현재 서버 계약과 공고의 상대 성별 조건을 구분하세요. 필터는 탐색 편의이고 신청 가능 여부는 서버가 계속 강제해야 합니다.
3. 인증 상태, 당도, 완료 동행 수, 공개 가능한 후기가 실제 데이터 계약에 맞게 표시되는지 확인하세요. 데이터가 없으면 숫자를 만들어내지 말고 빈 상태와 설명을 보여주세요.
4. `당도`가 무엇인지, 어떤 데이터가 반영되는지 도움말을 제공하세요. 아직 결정되지 않은 감점 수치나 신고 결과를 확정 정책처럼 쓰지 마세요.
5. 동행 확정 시 상태 변화가 목록·채팅·나의 동행에서 같은 용어와 시각적 강조로 보이게 하세요. 과도한 애니메이션은 `prefers-reduced-motion`을 존중하세요.
6. 채팅 첫 진입에 선택형 인사말 2~3개를 제공하되 자동 전송하지 말고 사용자가 편집·확정한 뒤 전송하게 하세요.

#### C. P2: 화면 이해와 입력 편의

1. 한 화면의 중복·동급 버튼을 정리하고 주요 행동 1개, 보조 행동을 구분하세요. 기능을 임의 삭제하지 말고 시각적 우선순위를 조정하세요.
2. 사용자에게 의미가 불분명한 `U` 같은 단독 영문 레이블을 행동이 드러나는 한글로 바꾸고, 하단 내비게이션의 언어를 통일하세요.
3. 팝업·모달에 닫기 버튼, 외부 영역 닫기, Escape 동작을 일관되게 제공하세요. 작성 중인 입력은 실수로 사라지지 않게 확인 절차를 두세요.
4. 날짜·시간·주소 입력의 레이블, 오류 문구, 키보드 접근성을 개선하세요. 주소 검색 외부 연동은 새 공급자를 임의 도입하지 말고 기존 계약 안에서만 처리하세요.
5. 공고 등록이 현재 한 화면에서 이해하기 어렵다면 기존 데이터를 유지하는 단계식 UI로 개선하세요. 뒤로 이동해도 입력이 보존되고 마지막 확인 단계에서 날짜·시간·장소·상대 조건을 요약해야 합니다.

### 5. 구현 방식

- 한 번에 전부 뜯어고치지 말고 `P0 → P1 → P2`의 수직 기능 단위로 진행하세요.
- 각 기능은 화면, 서버/RPC, 저장, 권한, 성공·실패 UI, 테스트를 함께 확인하세요.
- 스키마 변경이 필요하면 새 additive migration만 작성하세요. 로컬 테스트와 SQL 검토까지 마친 뒤, 실제 원격 적용 전에는 대상 ref·변경 SQL·데이터 영향·복구 방법을 사용자에게 보여주고 승인을 받으세요.
- 서로 독립적인 로컬 수정은 계속 진행하되, 제품 정책을 바꾸는 선택만 질문으로 분리하세요.
- 기존 변경을 `reset`, `checkout`, `restore`, 강제 push로 버리지 마세요.
