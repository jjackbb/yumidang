## 2026-09-21 추가 — 3·4차 시안의 API 영향

근거: [HTML 인수인계](../handoffs/화면구조_와이어프레임_HTML_2026-09-20.md)의 3·4차 보고. 이번 확인은 기록 열람이며 실제 API 호출은 NOT_RUN이다. 공급자·키 목록은 변경하지 않았다.

- **API-08 / 확정 진입 추가:** 공고 상세의 신청자 선택과 채팅의 수락이 같은 최종 확정 계약을 사용할 수 있는지 조사. 작성자 권한, 공고/신청 유효 상태, 두 사람의 일정 중복, 중복 요청·동시 수락을 서버에서 함께 처리하는 기존 범위/누락을 회신한다. D06 차단은 확정 기준이며 알림 세부는 정책 대기다. ‘마감’까지 확정 호출로 취급하지 말고 팀원 1의 상태 의미부터 맞춘다.
- **API-08 / 익명 모자이크:** 현재 HTML의 모자이크는 표현 시안이다. 사진을 내려준 뒤 흐리게 하는 것과 원본 사진·주소·식별자를 응답에 보내지 않는 것은 다르다. 최종 사진 공개 범위에 맞춰 이미지 URL·대체 텍스트·응답 필드·로그인 전환 시 캐시를 확인한다. 시안 모자이크를 서버 비노출 증거로 사용하지 않는다.
- **Q47 / 목록 계약:** 등록일·시작일 정렬, 작성자 나이 19~99 범위 필터, 익명 날짜 제한은 시안 반영 기록이 있으며 운영 정책은 회신 대기다. 현재 API 지원 여부·권한별 허용 조건·정렬 기준 시각과 빈값 처리를 조사한다. 작성자 나이 검색을 신청 자격 조건으로 대체하지 않는다.
- **ANON-03 / 확정 공개:** 당사자에게만 상대 이름과 안내를 주고 제3자에게는 확정 여부만 주는 계약 검토. 원본 이름을 새로 공개하지 않는다. 공개 공고·프로필·확정 약속 응답의 권한을 구분한다.
- **S10 / 시각 표시:** 상대 시각 표시는 프런트 표현이다. 서버는 기준 메시지의 시각을 제공하고 화면에서 변환하는 기존 계약을 확인한다. 시안 경계값 검사를 실제 메시지 시간 데이터 검증으로 보고하지 않는다.
- **모형과 실제 동작:** 4차 기록에서 정렬은 라벨 전환만, 나이 슬라이더는 고정 예시이며 실제 동작 미검증이다. UI가 있다는 이유로 API 필터·정렬 구현 완료로 세지 않는다.

## 화면 담당에게 가장 먼저 줄 데이터 계약

‘데이터 계약’은 화면이 받을 값과 빈값·오류의 의미를 서로 맞추는 약속이다. 다음은 초안이며 확정된 DB 컬럼/엔드포인트가 아니다.

| 기능 | 필요한 값 | 화면에서 꼭 구분할 상태 | 설계 경계 |
|---|---|---|---|
| 장소 검색 | 표시 이름, 공개 지역, 선택 식별자, 비공개 상세 위치 | 입력 전/검색 중/0건/선택/실패 | 일반 공고 응답에 상세 주소·정밀 좌표를 섞지 않는다. 소유자·확정 상대의 권한은 서버에서 확인 |
| 행사 목록·상세 | 내부/외부 ID, 출처, 제목, 4분류, 시작/종료, 지역, 이미지·권리, 원문 링크, 갱신 시각 | 예정/진행/종료/정보 부족/수집 실패 | 모르는 요금·일정·좌석은 추정하지 않는다. 순위는 출처·대상 기간·기준을 표시 |
| AI 브리핑 | 요약, 근거 후기 수, 갱신 시각, 상태 | 미연결/부족/생성 중/정상/실패/오래됨 | 공개 가능한 후기만. D-A16 캡션 고정. 실패·오래됨 표시 방식은 설계 검토 |
| 자연어 검색 | 해석 조건, 확인이 필요한 조건, 실제 검색 결과, 오류 유형 | 입력/해석 중/되묻기/조건 확인·수정/결과/0건/실패/한도 | 모델 출력은 허용 필드만 검증하고 검색한다. 신청·메시지 전송은 하지 않는다 |

각 계약에 **정상 1개, 빈 결과 1개, 오류 1개** 예시를 제공한다. 실제 응답이면 출처·확인 시각을, 합성 예시면 `설계용 예시`를 표시한다. 키가 없어도 합성 계약은 먼저 회신할 수 있다.

## 적용 순서와 완료 기준

1. **발급 준비:** 서비스별 계정 소유자·키 필요 여부·약관·한도·비용·도메인·환경을 기록한다. 계정 로그인·본인 인증·결제처럼 소유자만 할 수 있는 단계만 소유자에게 요청한다.
2. **발급과 설정:** 키는 서버 비밀값 저장소에 넣고, 문서에는 변수 이름·환경·등록 여부만 남긴다. 유료 전환·운영 데이터 사용처럼 새 선택이 필요한 일은 구체적인 범위와 비용을 제시한다.
3. **작은 연동부터:** 주소 선택/장소 검색 → 행사 공급자 하나의 목록·상세·빈 상태 → 나머지 공급자 → AI 어댑터 시험 순서를 제안한다. 이미 선택한 3개 행사 공급자를 임의로 축소하지 않는다.
4. **화면 계약 합의:** 팀원 1 정책 결과와 화면 목록을 맞춘다. 아직 없는 필드·정책을 화면이 있다고 가정하지 않게 한다.
5. **연결:** 기존 Supabase 구조를 보존하고 필요한 변경만 추가한다. 행사 식별·중복 제거·갱신 실패 복구, AI 캐시 무효화·삭제를 구현 범위에 포함한다.
6. **검증:** 실제 응답, 서버 권한, 비밀키 비노출, 0건·타임아웃·한도·재시도, 화면 연결을 각각 확인한다. 단위 테스트와 실제 API 성공을 구분한다.
7. **운영 반영:** 기존 승인·위임 범위에서 진행한다. 이 인수인계 작성 자체는 운영 DB 변경·키 교체·push 실행이 아니다. `main` push가 Production 배포로 이어지는 점을 실행 담당이 확인한다.

전체 UI 완성 때까지 API 가능성 확인을 미루지 않는다. 반대로 실제 API가 준비되지 않아도 화면 구조 합의는 합성 데이터·대기 표시로 계속한다.

## 정책/설계 담당과 맞출 사항

- P5: 행사 선택 범위·종료 행사 허용 여부. API의 조회 가능 범위와 제품 허용 범위는 다르다.
- P3·R1: 브리핑 최소 후기 수·부정 후기·삭제/비공개 전환 시 요약 무효화.
- AI-ENTRY·ANON-01~03: 비로그인 사용, 필터 권한. 작성자 이름 기반 표시값·성별/나이·상세 주소의 익명 공개 제한을 일반 검색뿐 아니라 AI 검색 결과에도 맞춘다. 사진·행사·일정 추가 제한은 정책 회신을 따른다.
- AI-DATA: 자유 후기의 개인정보 탐지·제거·미전송 처리, 공급자 보관/학습 조건. ‘이름 필드 제거’만으로 개인정보 미전송을 보장하지 않는다.
- AI-BUDGET: 요청량 가정 × 호출당 비용과 캐시 조건을 적어 비용 범위를 제안한다. **실측치/가정/미확인**을 구분한다.
- 8초 타임아웃, 1회 재시도, 3건 최소 후기, 하루 1회 갱신, 20건 입력은 기존 설계의 초안값이다. 검증·합의 없는 운영 상수로 확정하지 않는다.
- 공급자 장애가 기본 공고 검색·프로필 열람까지 막지 않게 한다. 요약의 사실 일치 여부는 사람이 표본 검수한다.

## 별도 범위 확인이 필요한 인증 연동

현재 로컬은 테스트 휴대폰 인증이다. **실제 SMS와 기관 이메일 발송 공급자는 이번 API 목록에서 확정된 서비스가 아니다.** Q48·Q49 검토와 함께 실제 제공 필요 여부를 보고한다. 필요하다면 공급자·본인 인증·비용·발신 조건·실제 수신 검증을 별도 작업으로 제안한다. Supabase URL·공개키가 있다고 실제 SMS가 발송되는 것은 아니다. KYC·결제·전화·캘린더 공급자를 미리 발급하거나 추가하지 않는다.

## 결과와 담당 AI 요청문

결과 파일 제안: `docs/api-integration/TEAM2_RESULTS.md`.

```text
API ID / 담당·계정 소유자 / 공식 문서·확인 날짜
발급 상태 / 로컬·검증·운영 환경별 설정 상태 (키 값 제외)
실제 호출 PASS·FAIL·NOT_RUN / 확인한 응답·오류 / 화면 연결 상태
계약 필드·예시 / 비용·한도 / 이용·저장·이미지 조건
정책 대기 / 남은 작업 / 변경 파일 / 운영 반영·복구 상태
```

완료 판정은 `발급`, `설정`, `서버 호출`, `화면 연결`, `운영 검증`을 각각 기록한다. ‘키 받음’을 ‘연동 완료’로 쓰지 않는다.

> 이 파일을 기준으로 팀원 2의 API 발급·연동을 도와줘. 고정 프로젝트를 확인하고 공식 문서에서 현재 조건을 검증해줘. 키 발급 전에도 화면용 필드·정상/빈값/오류 예시부터 회신해줘. 기존 정책과 공급자를 바꾸지 말고 새 선택이 필요한 부분만 이유와 대안을 제시해줘. 비밀키는 문서나 프런트에 넣지 말고, 실제 실행과 NOT_RUN을 나눠 결과를 남겨줘.
